## 1. 배포 방식 전환

### 1.1 업데이트 메커니즘 — GitHub zip 다운로드 (확정)

`git pull` vs zip 다운로드 vs "zip+로컬 재빌드" 하이브리드를 비교 검토해 **zip 다운로드**로
확정했다(git 설치 불필요, 하이브리드는 설치 부담·빌드 시간·백신 오탐만 늘고 이득 없음 — 근거는
`01c_infra_design.md` §1 표).

신규 모듈 `missa_updater.py`(leaf):

```python
REPO = "scottpark/missa_ppt"
BRANCH = "master"

def get_latest_commit_sha() -> str: ...   # GET api.github.com/repos/{REPO}/commits/{BRANCH}, 인증 불필요(public)
def check_for_update() -> tuple[bool, str]: ...  # config.json의 last_update_commit과 비교
def apply_update(sha: str) -> None: ...   # {REPO}/archive/{sha}.zip 다운로드 → 압축해제 →
                                           # 화이트리스트(*.py, assets/, missa_to_ppt.spec)만 복사
```

**절대 덮어쓰지 않음**: `config.json`, `output/`, `reference/`, `cache/`, `.git/`(있는 경우).

GUI에 "업데이트 확인" 버튼 추가 → `check_for_update()` → 있으면 확인 팝업 → `apply_update()` →
"다시 시작해 주세요" 안내.

### 1.2 배포 형태 — PyInstaller exe 폐기 → Python + `.bat` 런처 (확정)

exe는 `.py` 교체만으로 갱신되지 않으므로, **Python 인터프리터 직접 실행 + `.bat` 런처**로
전환한다.

```bat
:: run_missa.bat
@echo off
start "" pythonw.exe "%~dp0missa_to_ppt.py"
```

`pythonw.exe`(창 없는 Python)라 콘솔이 뜨지 않는다. 바탕화면 바로가기(.lnk)가 이 `.bat`를
가리키게 하고, 바로가기 아이콘을 기존 성당 로고로 지정하면 사용자 체감은 지금 exe와 동일하다.

**대상 PC 최초 1회 준비**: Python 설치 + `pip install -r requirements.txt` + 저장소 zip
다운로드(또는 클론). 설치 안내 스크립트(`install.bat`)를 함께 만든다.

## 2. OneDrive 연동 — Microsoft Graph API, Device Code Flow

### 2.1 인증 (확정: 성당 공용 계정 1개)

개인별 로그인 분기 불필요. **Device Code Flow**(MSAL Python, `msal` 패키지) 채택:
- Azure AD에 **퍼블릭 클라이언트**로 앱 등록(client secret 불필요 — public repo에 client ID를
  노출해도 안전, client ID는 비밀이 아님).
- 스코프: `Files.ReadWrite`, `offline_access`.
- 최초 실행 시 코드 표시 → 담당자가 공용 계정으로 `microsoft.com/devicelogin`에서 로그인 →
  토큰 수신. 토큰 캐시(`msal_token_cache.bin`, `.gitignore` 등록)로 재로그인 최소화.
- **Azure AD 앱 등록 실무는 보류** — 사용자가 계정 준비되는 대로 별도 안내 예정. 등록 전까지
  이 부분 구현은 시작할 수 없음(선행 조건).

### 2.2 `missa_onedrive.py` (신규 모듈, leaf) — **구현 완료(2026-09-18)**

```python
def get_access_token() -> str: ...              # MSAL 캐시 우선, 없으면 device code flow
def list_children(path: str) -> list: ...        # GET /me/drive/root:/{path}:/children (페이지네이션 자동 병합)
def download_file(path: str, dest: Path) -> Path: ...  # GET .../content
def upload_file(path: str, local_path: Path) -> None: ...  # PUT .../content (≤250MB 단순 업로드로 충분)
def ensure_folder(path: str) -> None: ...        # 세그먼트별 존재확인(GET) 후 없을 때만 생성(POST, 409는 정상 처리)
```

`CLIENT_ID`/`AUTHORITY`(`https://login.microsoftonline.com/consumers`)는 §2.1에서 이미
등록·검증된 값(App ID `21b7d1a4-87bb-4148-8ae8-8b57231c125b`)을 그대로 상수로 박아뒀다.
`SCOPES=["Files.ReadWrite"]`만 명시하고 `offline_access`는 별도로 넣지 않았다 — MSAL이
공개 클라이언트에서 `openid`/`profile`/`offline_access`를 자동으로 추가해 refresh_token을
내려준다는 사실을 이전 라운드 MSAL 실측 스크립트(§2.1 검증 기록)로 이미 확인했기 때문이다.
토큰 캐시는 `msal_token_cache.bin`(`.gitignore` 등록 완료)에 `MSAL SerializableTokenCache`로
저장, `has_state_changed`일 때만 디스크에 쓴다(무의미한 매 호출 쓰기 방지).

테스트는 `test_missa_onedrive.py`(23개, O1~O11 — 2026-09-26 O7~O11 9개 추가, 아래 참고) —
실제 네트워크·MSAL 로그인은 전혀 발생시키지 않고 `requests.get/put/post`와
`msal.PublicClientApplication`을 전부 monkeypatch로 대체해 순수 로직(경로 URL 조합·URL
인코딩·페이지네이션 병합·캐시 우선 인증·device flow 폴백·에러 래핑·폴더 생성 멱등성)만
검증한다(`missa_updater.py`/`test_missa_updater.py`와 동일 방식). §13 참고 — 실제 Graph
API 호출을 통한 end-to-end 검증은 2026-09-26에 처음 수행했고(`ensure_folder`→`upload_file`
실제 왕복, 아래 remoteItem 항목 참고), 그 검증에서 진짜 버그가 하나 드러났다.

**2026-09-26 발견·수정 — `PPT 문서`가 진짜 폴더가 아니라 공유 바로가기(remoteItem)였다.**
E1(청년미사 결과 PPT OneDrive 자동 업로드, §4/§13-5)이 실제 라이브 Graph API에서 404로
실패해 코디네이터가 직접 Graph API를 호출해 원인을 확정했다: 성당 공용 계정
(`brokenbaykccppt@gmail.com`)의 OneDrive에서 최상위 경로 `PPT 문서`는 진짜 폴더가 아니라
**다른 드라이브를 가리키는 공유 바로가기(remoteItem)**다. `GET /me/drive/root:/PPT 문서:`는
200을 반환하지만 `folder` 파셋 없이 `remoteItem`(`id`, `parentReference.driveId`) 파셋만
있고, 이 모듈이 쓰던 경로 기반 주소(`root:/PPT 문서/...:`)는 이 바로가기 뒤를 이어붙이지
못해 하위 경로 조회가 404(GET)/422(children)로 실패했다 —
`/drives/{driveId}/items/{itemId}/...` 형태로 주소 체계를 전환해야 실제 하위 폴더에
닿는다. `list_children`/`ensure_folder`/`upload_file`/`download_file` 4개 함수 전부
`_item_url()`을 거치므로 전부 영향을 받았다(E1 하나만의 버그가 아니라 모듈 전체의 버그) —
§2.4의 로컬 동기화 우선 폴백이 지금까지 이를 가려온 것으로 보인다.

수정: `_resolve_remote_base(first_segment)`(신규)가 첫 경로 세그먼트에 대해 실제 GET으로
remoteItem 여부를 확인해 `(driveId, itemId)`|`None`을 `_REMOTE_ITEM_CACHE`(프로세스 수명
캐시)에 저장하고, `_ensure_base_resolved(path)`(신규, 얇은 헬퍼)를 4개 공개 함수 모두 URL
생성 전에 호출한다. `_item_url()` 자체는 **순수 함수로 유지**했다 — 이 함수가 직접
네트워크 GET을 하게 만들면 모킹 없이 `_item_url()`을 직접 호출해 순수 문자열 변환만
검증하던 기존 테스트(O1/O1b/O1c)가 깨지고 함수의 기존 계약도 깨지므로, 해석(네트워크)과
URL 조립(순수 문자열)을 분리했다 — `_item_url()`은 `_REMOTE_ITEM_CACHE`를 읽기만 해서
캐시에 있으면 `/drives/{id}/items/{id}...`, 없으면 기존 `root:/...:` 그대로 반환한다.
404는 `_resolve_remote_base()`에서 raise하지 않고 None으로 처리 — 진짜 "경로 없음" 에러
메시지는 호출부의 기존 404 처리가 담당해야 하기 때문이다. 실측 검증: `list_children('PPT
문서/20.청년 미사')`(3개 항목 정상 조회) → `ensure_folder('PPT 문서/20.청년 미사/2026')` →
`upload_file(...)` 왕복이 실제로 성공함을 확인했고, F그룹 CLI(`20260926 --미사유형 청년`)를
재실행해 `[8.5] OneDrive 업로드...`가 404 경고 대신 실제 성공 메시지로 바뀐 것도 직접
확인했다. 상세는 CLAUDE.md `missa_onedrive.py` 모듈 설명, `_workspace/02_specialist_impl_
notes.md` "F그룹 후속" 절 참고.

**2026-09-26 발견·수정(G2) — OneDrive 커스텀 파일 브라우저(§2.3)가 폴더 열 때마다
3~6초씩 느린 문제.** 근본 원인은 `get_access_token()`이 호출될 때마다
`msal.PublicClientApplication(CLIENT_ID, authority=AUTHORITY, token_cache=cache)`를
**매번 새로 생성**한 것 — 이 생성 자체가 약 0.9~1.0초 걸린다(코디네이터 실측,
`AUTHORITY`가 네트워크 기반 authority라 생성자 안에서 매번 instance discovery를 재수행하는
것으로 추정). 그 뒤의 `acquire_token_silent()`는 0초라 토큰/캐시 파일 문제가 아니라 "매번
새 오브젝트를 만드는 것 자체"가 병목이었다. `_headers()`가 모든 공개 함수(`list_children`
등)에서 매 HTTP 요청마다 `get_access_token()`을 다시 부르므로, 폴더 하나를 열 때 children
GET + remoteItem 해석 GET처럼 여러 요청이 겹치면 이 오버헤드가 누적됐다.

`_APP_CACHE = [None, None]`(모듈 레벨 `[app, cache]`)와 `_get_app()`(최초 호출에서만
`_load_cache()`+`PublicClientApplication()` 생성, 이후 재사용) 신규 추가 —
`get_access_token()`은 `app, cache = _get_app()`으로 바꾸고 나머지 로그인 로직(silent/
device flow/`_save_cache`)은 전혀 손대지 않았다. `list_children`/`ensure_folder`/
`upload_file`/`download_file`/`_resolve_remote_base` 등 `_headers()`를 거치는 모든 호출부가
코드 수정 없이 자동으로 이득을 본다(MSAL 공식 권장 사용 패턴이기도 함). 실측: 앱 생성 단독
1.131초 → 캐시 재사용 0.000000초, `list_children` 반복 호출 6.361초(콜드) → 2.06~2.22초
(재사용, 순수 네트워크 왕복만 남음). `_APP_CACHE`가 프로세스 수명 캐시라 기존
`test_missa_onedrive.py`의 O2b/O2c가 실행 순서에 의존하게 돼 실제로 깨졌던 것을 파일 전체
`autouse` fixture로 격리해 수정(상세: `_workspace/02_specialist_impl_notes.md` "G그룹" 절).

### 2.3 수동 "찾아보기" 대체 UI — **2026-09-24 재도입: 청년미사 참조 PPT/화답송 등 입력 파일 선택에 Treeview 브라우저 구현**

2026-09-18 시점에는 "계정 1개·경로 고정이라 탐색 UI가 불필요"하다고 판단해 자동 전체
미러링(§2.4)만으로 충분하다고 봤다. 그러나 이는 **성가 PDF/PPT 원본**(경로가 고정된
폴더 트리) 이야기였고, `_ask_combined_input_popup()`의 **참조 PPT/화답송/시작기도/공지사항**
같은 "그 주에만 존재하는 개별 파일"은 사정이 다르다 — 청년미사는 성인미사처럼
`output/{date}/` 로컬 폴더에 파일이 미리 준비돼 있지 않고, 매주 OneDrive의 특정 하위
폴더에서 사용자가 그때그때 골라야 한다. 이 요구를 반영해 2026-09-24(B/A/C/D 확장
라운드, A5)에서 **`_ask_onedrive_file_browser_popup(parent, dest_dir, root_remote_path,
cache=None)`을 신규 구현**했다 — 원래 설계 초안의 함수명(`_ask_onedrive_browse_popup`)과는
다르지만 목적은 동일한 Tkinter `Treeview` 기반 폴더 탐색 팝업이다. 차이점: "위로" 버튼
대신 더블클릭 lazy-load(자리표시자 자식으로 펼침 화살표 표시 후 실제 자식으로 교체) 방식을
쓰고, 시작 위치는 `list_children('PPT 문서')` 결과를 트리 최상위에 바로 렌더링한다("PPT
문서" 폴더 자체는 노드로 노출하지 않음, 사용자 추가 지시). 선택한 파일은
`missa_onedrive.download_file()`로 그 미사의 출력 폴더(§4, B그룹 규칙 적용)에 내려받아
기존 `files` 딕셔너리 흐름에 그대로 합류한다. 폴더 목록은 세션 내 메모리 캐시(`_od_cache`,
행마다 공유)로 중복 조회를 피한다. **성인미사는 이 팝업을 전혀 타지 않고 기존 로컬
`filedialog.askopenfilename` 그대로 유지**(`mass_type` 분기).

성가 PDF/PPT 원본(나주노/야훼이레/가톨릭성가) 쪽은 여전히 §2.4의 **자동 전체 미러링**이
담당한다 — 이 구조는 2026-09-18 결정 그대로 변경 없음. 즉 "고정 폴더 트리 원본"과 "매주
바뀌는 개별 파일 선택"이라는 서로 다른 두 요구를 각각 다른 메커니즘(미러링 vs 탐색 UI)으로
푼 것이며, 서로 대체 관계가 아니라 공존 관계다.

**2026-09-26 발견·수정(H그룹) — 폴더 확장 화살표(단일 클릭)로는 자식이 영구히 "(불러오는
중...)"에서 멈추는 버그.** `_on_double_click`이 lazy-load fetch를 `<Double-1>`에만
바인딩해뒀는데, ttk.Treeview의 확장 화살표(▶/▼ indicator) 단일 클릭은 `<Double-1>`과
무관한 네이티브 Tk 토글이라 이미 삽입해둔 자리표시자 자식을 그대로 보여주기만 하고
`_on_double_click`을 호출하지 않는다 — 실제 `list_children()` fetch가 일어나지 않아
자리표시자가 영구히 남는다(코디네이터가 실사용 스크린샷으로 확인). "이미 로드됐는지 확인 →
자리표시자 삭제 → 자식 삽입" 로직을 `_ensure_folder_children_loaded(iid)`로 추출해
`_on_double_click`과 신규 핸들러가 공유하도록 하고, 화살표 클릭·더블클릭·키보드 등 펼치는
방법과 무관하게 항상 발생하는 `<<TreeviewOpen>>` 가상 이벤트에 새 핸들러를 바인딩했다(대상
iid는 `tree.focus()`로 획득, open 상태는 수동 토글하지 않음 — 이벤트 발생 시점에 Tk가 이미
네이티브로 전환을 마친 뒤라 재토글하면 되닫힘 위험). 기존 더블클릭 경로도 여전히 폴더
펼침을 유발하지만 `already_loaded` 가드가 공유 헬퍼 안에 남아 있어 두 경로가 겹쳐도
fetch는 최대 1회다. 상세: `_workspace/02_specialist_impl_notes.md` "H그룹" 절.

**후속 후보(이번 라운드 범위 밖, 미착수)**: (1) 폴더 확장 fetch가 여전히 Tk 메인 스레드

워커스레드+폴링 패턴을 재사용해 백그라운드화할 수 있다(`_ensure_folder_children_loaded`가

부수 관찰로 지적한 사항 — 네트워크 오류로 fetch가 실패하면 `messagebox.showerror` 이후

**2026-09-26 발견·수정(I그룹) — OneDrive에서 파일 선택 후, 입력 확인 화면의 경로 표시가
비실용적인 문제.** `_ask_combined_input_popup(mass_type='youth')`의 '찾아보기'가
`_ask_onedrive_file_browser_popup()`이 반환한 **로컬 다운로드 경로**
(`output\{date}_youth\{파일명}`)를 그대로 46자 폭 Entry에 표시해, 모든 청년미사 파일에
공통인 접두사 때문에 정작 파일을 구분하는 부분(파일명)이 Entry 밖으로 잘려 안 보였다
(실사용자 스크린샷으로 확인). 사용자 확인을 거친 요구사항대로 (1) 표시를 `PPT 문서/`
접두사를 뺀 OneDrive 상대경로로(예: `13. 기도문\위령 성월 기도.pptx`), (2) 파일명이 최소
절반 이상 보이도록 Entry를 끝까지 스크롤하는 것으로 바꿨다.

핵심 설계 제약은 "표시 문자열과 파이프라인이 실제로 쓰는 값의 분리"다 — Entry의
`textvariable`이 곧 `on_ok()`가 읽는 `vars_[key]`이므로, 표시를 상대경로로 바꾸면 존재하지
않는 경로를 그대로 파일 처리에 넘기는 회귀가 생긴다. 세 함수로 분리해 해결했다:
`_onedrive_display_path()`(표시 문자열 생성, `_ONEDRIVE_BROWSER_ROOT` 상수 재사용),
`_resolved_field_value()`(on_ok()의 모든 필드 조회가 거치는 단일 지점 — 별도 dict
`_od_real_paths`에 실제 로컬 경로가 있으면 그걸 우선), `_apply_onedrive_selection()`
(`_browse()`가 해야 하는 3가지 부작용을 한 곳에: real path 저장·표시 문자열 설정·Entry
스크롤). `_ask_onedrive_file_browser_popup()`의 반환 타입을 `str` → `(local_path,
remote_path)` 튜플로 확장(표시용 상대경로를 만들려면 remote_path가 필요해짐, 취소 시
`('', '')`) — 호출부가 한 곳뿐임을 grep으로 재확인한 뒤 안전하게 변경했다. 3개 함수 모두
GUI 없이 순수/duck-typed 단위 테스트가 가능하다(`test_i1`~`test_i9`). 상세: `_workspace/
02_specialist_impl_notes.md` "I그룹" 절, CLAUDE.md의 "표시 문자열과 실제 처리값은 반드시
분리한다" 일반 원칙.

**2026-09-27 발견·수정(K1) — OneDrive 브라우저 재귀 프리페치.** §J5(선택 구현)의
`_prefetch_onedrive_children()`은 3개 허용 루트 폴더의 **직계** 자식만 백그라운드로
캐시에 채웠다 — 하위 폴더로 들어가면 여전히 동기 `list_children()` 호출이 걸려 팝업이
멈췄다. 모든 하위 폴더/파일을 재귀적으로 한 번에 캐시에 채우도록 확장: `_cached_
onedrive_children()`으로 한 경로를 채운 뒤, 반환된 children 중 `'folder' in item`인
것만 다음 재귀 호출의 입력으로 넘긴다. 개별 폴더 조회가 실패하면(네트워크 오류 등)
`continue`로 건너뛰어 그 아래로는 재귀하지 않는다(존재하지 않는 children으로 재귀할
데이터가 없다) — §J5의 "실패해도 나머지는 계속 시도" 원칙을 재귀 깊이에도 그대로
확장한 것이다. `<<TreeviewOpen>>`(§H그룹)이 거치는 `_ensure_folder_children_loaded()`
→`_insert_children()`→`_cached_onedrive_children()`은 이미 "캐시에 있으면 네트워크
스킵" 계약을 갖고 있어, 이 확장 하나만으로 하위 폴더 탐색도 캐시 히트가 된다(별도
수정 불필요).

구현 전 실측(코디네이터 요청 — "재귀 깊이·API 호출 횟수가 커질 수 있으니 레이트리밋/
타임아웃에 대한 현실적 예상을 남겨달라"): 실제 3개 허용 루트 폴더 트리를 같은 방식
(순차 재귀, `missa_onedrive.list_children()` 그대로)으로 조회한 결과 총 API 호출
9회·하위폴더 6개(루트 3개 제외)·파일 31개·최대 깊이 2·순차 총 22.04초(평균 2.449초/
호출, 응답 시간의 대부분은 네트워크 왕복 지연). 이 규모면 동시 요청 없이 순차 재귀만
으로도 429/타임아웃 위험이 없고, 백그라운드 스레드에서 사용자가 날짜·미사유형을
입력하는 동안 끝나기에 충분히 빨라 **병렬화하지 않기로 결정**했다 — 트리가 실제로
훨씬 커지면 재검토가 필요하다는 전제를 주석에 남겼다.

**2026-09-27 신규(K2) — OneDrive 파일 로컬 캐시 재사용.** OneDrive 브라우저로 받는
파일(공지사항/시작기도/미사후기도/성가 PPT 등, 파일 종류로 분기하지 않음)을 매번
재다운로드하지 않고, 로컬에 캐시가 있고 OneDrive 쪽이 변경되지 않았으면 재사용한다.
날짜 폴더(`output/{date}_youth/`)와 별개인 공유 캐시 폴더(`_ONEDRIVE_CACHE_ROOT =
'onedrive_cache'`)에 원본 1부를 보관해, 이번 주 시작기도와 다음 주 시작기도가 같은
파일이면(변경 없음) 재다운로드 없이 재사용할 수 있게 한다. 캐시 히트/미스 어느 쪽이든
마지막엔 날짜 폴더로 복사해 반환 — 기존 파이프라인이 "날짜 폴더 경로"를 기대하는
가정을 깨지 않는다.

`missa_onedrive.get_item_metadata(path)`(children 없이 항목 메타데이터만 GET, 404→
FileNotFoundError, `list_children`/`download_file`과 동일 에러 관례) 신설. 실제 응답을
직접 조회해 `lastModifiedDateTime`/`eTag` 둘 다 존재함을 확인했고, `lastModifiedDateTime`
**문자열 완전일치**만을 신선도 판단 기준으로 채택했다(파싱해서 "더 최신인가"를 비교하지
않음 — 타임존/포맷 파싱 버그 여지를 원천 차단하고, "조금이라도 다르면 재다운로드"라는
안전 우선 불변조건을 가장 단순하게 만족). 매니페스트(`onedrive_cache/manifest.json`,
`{remote_path: {lastModifiedDateTime, eTag}}`) + `_onedrive_cache_blob_path()`(remote_
path를 sha1 해시해 캐시 폴더 안 고정 파일 하나로 대응 — 경로가 다른 동명 파일이 캐시
폴더 안에서 충돌하지 않도록) + `_resolve_onedrive_download()`(매니페스트 기록 + 원격
메타데이터 + 캐시본 존재를 모두 만족하고 `lastModifiedDateTime`이 완전일치할 때만
재사용, 그 외 전부 안전하게 재다운로드 후 매니페스트 갱신). `_on_choose()`가 기존
`_download_onedrive_selection()`(무조건 재다운로드, 하위호환용으로 그대로 남김) 대신
이 함수를 호출하도록 교체.

**리뷰 라운드17 확정 버그(K1/K2 시너지가 핵심 불변조건을 깨는 경로) — 발견·수정.**
최초 구현은 K2의 신선도 판단(`_lookup_remote_item_metadata()`)이 K1의 재귀 프리페치가
채운 `cache[parent_path]`(부모 폴더 children 목록, 각 항목에 `lastModifiedDateTime`
포함)에 매칭되는 항목이 있으면 그걸 "실시간 메타데이터"로 오인해 `get_item_metadata()`
실시간 호출 자체를 건너뛰도록 구현됐다("K1/K2 시너지"로 API 호출을 아낀다는 의도).
독립 리뷰가 이 시너지 자체를 의심해 코드 수정 없이 `_resolve_onedrive_download()`를
직접 호출해 재현: 로컬 매니페스트 기록과 K1 캐시가 둘 다 지난주 스냅샷으로 "서로는"
일치하는데, 실제 OneDrive는 그 사이 바뀐 상태(오늘 날짜)로 스텁 — 재다운로드가
스킵되고 stale 콘텐츠가 반환됨을 확인했다. K1 캐시는 프리페치(또는 사용자가 폴더를
한 번 펼친) 시점에 고정된 스냅샷이라 팝업이 열려 있는 동안 전혀 갱신되지 않는데
(`_cached_onedrive_children()`의 "이미 있으면 재사용" 계약 때문), 정확히 이 경우에
"OneDrive가 더 최신이면 이름이 같아도 반드시 재다운로드"라는 사용자 명시 핵심
불변조건이 깨진 것이다.

수정: `_lookup_remote_item_metadata()`를 완전히 삭제하고, `_resolve_onedrive_download()`
가 `cache` 인자와 무관하게 항상 `missa_onedrive.get_item_metadata(remote_path)`를
직접·실시간으로 호출하도록 변경했다. K1의 `cache`는 이제 이 함수의 최종 판단에 전혀
관여하지 않고, 트리 UI 표시(폴더 확장 시 네트워크 스킵)라는 원래 목적으로만 쓰인다.
다운로드 대상 파일 1개당 `get_item_metadata()` 정확히 1회만 추가로 호출되므로 API
비용 증가는 무시할 수준이다. 일반화된 원칙("서로 다른 목적의 캐시 계층이 겹칠 때, 한
계층의 스냅샷을 다른 계층의 최종 판단에 재사용하지 않는다")은 CLAUDE.md와 `docs/
ooxml-pitfalls-log.md`에 신설. 상세: `_workspace/02_specialist_impl_notes.md` "K그룹"/
"K그룹 리뷰 라운드17 재작업" 절.

**2026-09-27 신규(L1) — OneDrive 프리페치 조기 트리거.** K1의 재귀 프리페치는
`_ask_onedrive_file_browser_popup()`(사용자가 "찾아보기"를 눌러야 열리는 팝업)이 열릴
때만 시작됐다 — 그 사이의 캐시 예열 시간이 짧을수록 실제 파일 목록 조회 시 캐시 히트
확률이 낮았다. 기존 인라인 스레드 시작 코드를 `_start_onedrive_prefetch_thread(cache,
root_remote_path=_ONEDRIVE_BROWSER_ROOT)` 공유 헬퍼로 추출하고, `_ask_combined_input_
popup()`이 창을 띄우는(`root.deiconify()`) 직후(청년미사만) 이를 논블로킹으로 호출하도록
배선을 앞당겼다. 스레드 시작 자체가 블로킹하지 않으므로 로그인이 안 돼 있거나(MSAL 기기
코드 로그인 대기) 네트워크가 없어도 첫 입력창은 항상 즉시 뜬다 — 실패는 `_prefetch_
onedrive_children()`이 이미 경로 단위로 조용히 삼킨다(§J5). `_ask_onedrive_file_browser_
popup()`도 같은 헬퍼를 그대로 호출해 2차 안전망 역할을 유지하며, 같은 `cache` dict를
공유하므로 두 트리거가 겹쳐도 중복 네트워크 호출은 최소화된다.

**2026-09-27 신규(L2) — 파일 선택 즉시 반환 + 백그라운드 다운로드.** K2까지는
`_on_choose()`가 그 자리에서 `_resolve_onedrive_download()`를 호출해 다운로드가 끝나야
팝업이 닫혔다 — 파일이 크거나 네트워크가 느리면 사용자가 다음 파일을 고르기까지 기다려야
했다. `_on_choose()`를 다운로드 없이 결정적 목적지 경로만 계산해 즉시 반환하도록 바꾸고,
호출부(`_ask_combined_input_popup()`의 `_browse()`)가 generation 기반 `_download_state`
(`{key: {generation, status, error, thread}}`)로 백그라운드 스레드(`_download_worker`)에
실제 다운로드를 맡긴다. `generation`은 같은 슬롯을 재선택할 때마다 증가시켜, 먼저
시작한(느린) 다운로드가 나중에 끝나도 최신 선택의 상태를 덮어쓰지 못하게 한다(코디네이터
명시 요구사항 — "가장 마지막 선택만 유효해야 함"). `_download_with_retries()`(K2의
신선도 확인 로직을 `_ensure_onedrive_blob_fresh()`로 분리해 재사용, 최대 2회 자동
재시도·backoff 없음)로 재시도하고, "확인" 클릭 시 `_wait_for_pending_downloads_or_
report_failure()`가 미완료 다운로드를 전부 대기(재시도 루프가 유한해 무한 대기가 되지
않음)한 뒤 실패 항목이 있으면 알리고 팝업을 유지한다.

**리뷰 라운드19 확정 버그 — "마지막 선택만 유효"가 디스크 파일 수준에서는 깨짐.**
최초 구현은 generation 재확인이 메모리 상태(`_download_state`)만 보호했을 뿐, 실제
디스크 목적지 커밋(`_resolve_onedrive_download()`가 그 자리에서 바로 dest_dir에 복사)은
generation과 무관하게 무조건 일어났다. 같은 슬롯을 같은 파일명으로 재선택하면(이 앱에서
"시작기도.pptx"/"미사 후 기도.pptx"/"공지사항 PPT" 계열이 매주 다른 폴더에서 같은 이름
으로 반복되는 게 정상 관례) 목적지 경로가 remote_path가 아니라 파일명만으로 결정되므로,
구세대(느린) 스레드가 추적에서 빠진 채 백그라운드에서 계속 돌다가 "확인"이 이미 성공을
선언하고 팝업이 닫힌 뒤 최신 파일을 조용히 자신의 구식 내용으로 덮어쓸 수 있었다. 독립
리뷰가 서브프로세스 Tk 프로브로 직접 재현했다: 1차 선택(느림, 1.5초 후 완료)을 같은
파일명으로 재선택(빠름, 0.1초 후 완료)하면, "확인" 클릭 0.31초 후엔 최신 선택 내용이
맞지만 2초 더 기다리면 파일 내용이 옛 선택으로 조용히 역전됐다(에러 콜백 없음). 기존
`test_l2f`는 두 선택에 의도적으로 다른 파일명(`file1.pptx`/`file2.pptx`)을 써서 이
충돌 경로를 구조적으로 피해가고 있었다.

수정: "blob 최신화"(`_ensure_onedrive_blob_fresh()`, generation 무관·공유 캐시 폴더만
다루므로 안전)와 "blob→목적지 커밋"(`_commit_onedrive_blob_to_dest()`, 순수 파일 복사)을
분리하고, 커밋 자체를 `_download_worker`가 `_download_lock` 안에서 generation을 재확인한
경우에만 수행하도록 재작성했다 — 재확인에 실패하면(재선택으로 낡은 세대) 아무것도
건드리지 않고 return한다. `_resolve_onedrive_download()`는 이 둘의 합성으로 재작성됐지만
외부 계약은 그대로라 K그룹 기존 테스트는 무변경으로 통과한다. 같은 파일명 재선택
시나리오를 커버하는 `test_l2g`를 신규 추가했고, 독립 재리뷰(라운드20)가 `_download_
worker`를 라운드19 이전 순서로 일시 되돌려 정확히 같은 증상으로 실패함을 재현한 뒤
원상복구해 재통과를 확인했다. 상세: `_workspace/02_specialist_impl_notes.md` "L그룹"/
"L그룹 리뷰 라운드19 재작업" 절, `_workspace/02b_review_report.md` 라운드19/20.

### 2.4 `config.json` 스키마 — **구현 완료(2026-09-18): 신규 키 추가, 기존 키는 유지(대체 아님)**

당초 표는 기존 키를 신규 키로 "교체"하는 것처럼 보였으나, 실제로는 **둘 다 공존**하며
우선순위로 동작한다(`missa_gui._resolve_onedrive_folder()`): (1) 기존 로컬 절대경로 키가
유효하면 그대로 쓰고(Scott PC 등 이미 동작 중인 환경은 무변경, Graph API를 아예 안 탐) →
(2) 없으면 신규 상대경로 키(또는 하드코딩된 기본값)로 Graph API 미러링 → (3) 그래도 실패하면
기존 수동 폴더 선택 팝업. 로컬 키를 삭제해버리면 Scott PC를 포함한 기존 환경이 매번
불필요하게 Graph API를 타게 돼 위험하다고 판단했다.

| 로컬 절대경로 키(1순위, 기존 그대로) | 원격 상대경로 키(2순위, 신규 — 생략 시 하드코딩 기본값 사용) |
|---|---|
| `onedrive_hymn_folder` | `onedrive_hymn_path` (기본값: `PPT 문서/09.가톨릭 성가/성가-악보버전`) |
| `onedrive_youth_hymn_folder`(2026-09-15 로컬 동기화 폴더 fix에서 추가) | `onedrive_youth_hymn_path`(기본값: `PPT 문서/20.청년 미사/2.성가`) |

가톨릭성가 폴더가 청년미사 공용 계정(`brokenbaykccppt@gmail.com`)에도 동일 구조로 존재함을
사용자가 직접 확인해줬다(2026-09-18) — 그래서 `get_onedrive_hymn_folder()`(성인미사와
청년미사 '가톨릭성가' 출처가 공유)도 안전하게 같은 계정의 Graph API로 전환할 수 있었다.

**미러링 범위와 알려진 제약**: `_mirror_onedrive_folder()`는 확장자를 가리지 않고 폴더
트리 전체(하위 폴더 포함)를 재귀적으로, 이미 로컬에 있는 파일은 건너뛰며(증분) 로컬 캐시로
복사한다. `missa_youth_hymn_pdf.py`는 전혀 손대지 않았다 — `get_onedrive_youth_hymn_root()`가
반환하는 Path가 실제 동기화 폴더든 미러링된 캐시든 구분 없이 그대로 동작하기 때문이다(PDF
원본도 같은 폴더 트리 안에 있어 자동으로 미러링 대상에 포함됨).

**의도적으로 범위에서 뺀 것 — 캐시 역방향 동기화(쓰기) 미구현**: `resolve_youth_hymn_pptx()`가
나주노/야훼이레 PDF에서 새로 만든 성가 PPT를 로컬 동기화 폴더에 저장하면(Scott PC처럼 실제
OneDrive 동기화 중인 환경) OneDrive 앱이 알아서 업로드해준다. 반면 Graph API 미러링 캐시로
동작하는 배포 PC에서는 이 저장이 **로컬 캐시에만** 남고 OneDrive로 다시 업로드되지 않는다 —
그 PC에서는 다음 주에도 재사용되지만(로컬 캐시가 남아있으므로), 다른 PC들과는 공유되지
않는다. 오늘 이전에는 이런 PC들이 아예 OneDrive를 읽지도 못했으므로 이건 회귀가 아니라
"아직 완성하지 않은 개선"이다. 필요해지면 `missa_onedrive.upload_file()`로 후속 구현
가능(§13 후속 과제).

**주의**: `missa_youth_hymn_pdf._resolve_pdf_path()`(2026-09-15 구현, 로컬 동기화 폴더 기반)는
이 전환과 함께 `missa_onedrive.download_file()`을 쓰도록 다시 손봐야 한다. `reference/청년미사/`
로컬 사본 우선 확인 로직은 유지(개발 PC 빠른 경로).

## 5. `find_sections()` 확장 — 청년미사 템플릿 실측 기반

| ③ 2차봉헌을 5종에 포함 | `required = HYMN_TYPES if is_sunday else [...]` | **True**(템플릿에 항상 존재) |
| ④ 성가 실제 악보 복사(vs 번호만 갱신) | `find_files()`, `replace_성가(copy_scores=)` | **True** |

청년미사가 원하는 조합 `(①False, ②True, ③True, ④True)`은 기존 주일(전부 True 계열)도
평일(①②만 False 계열)도 아닌 **제3의 조합**이라, 리더가 지시한 "2개 플래그 분리"만으로는
부족함을 실측으로 확인했다. 그래서 ③·④는 별도 명명된 플래그로 만들지 않고 **`mass_type`에서
직접 도출**해, 어느 것도 ①로부터 암묵적으로 유도되지 않게 한다(핵심: "우연히 값이 같다"에
기대지 않음).

### 8.2 최종 설계

```python
# missa_to_ppt.py main() — 기존 단일 is_sunday 변수를 대체
is_calendar_sunday = is_sunday_mass(date_str)                      # ① 순수 달력 판정, 의미 불변

if mass_type == 'adult':
    use_weekday_display = not is_calendar_sunday                  # ② 기존과 동일(달력 연동)
    include_2차봉헌      = is_calendar_sunday                      # ③ 기존과 동일
    copy_hymn_scores     = is_calendar_sunday                      # ④ 기존과 동일
else:  # 'youth'
    use_weekday_display = True                                    # ② 요구사항 §6.2/§6.5 고정
    include_2차봉헌      = True                                    # ③ 템플릿 구조상 고정
    copy_hymn_scores     = True                                    # ④ 요구사항 §5 고정
```

adult 경로는 4개 값 전부 `is_calendar_sunday`(또는 부정)로만 정의되므로 **기존 동작과 100%
동일**(순수 변수 분리, 로직 변경 없음 — 회귀 테스트로 확정 확인).

### 8.3 호출부 치환

| 기존 | 변경 후 |
|---|---|
| `required = HYMN_TYPES if is_sunday else [...]` | `if include_2차봉헌` |
| `find_files(date_str, hymn_numbers, is_sunday)` | `find_files(..., copy_hymn_scores)`(매개변수명도 리네임 — §8.4) |
| `update_화답송(..., is_sunday=is_sunday)` | `update_화답송(..., is_sunday=not use_weekday_display)`(**구현 단계에서 발견·수정된 부호 오류** — 아래 8.3.1 참고. 함수 내부 매개변수명은 "주일 포맷(악보 포함)인가"라는 단일 의미라 유지, §8.5) |
| `replace_성가(..., copy_scores=is_sunday)` | `replace_성가(..., copy_scores=copy_hymn_scores)` |
| `if not is_sunday and files.get('미사후기도')` | `if use_weekday_display and files.get('미사후기도')` |
| `validate(..., is_sunday=is_sunday)` | `validate(prs2, json_data)` — **구현 단계에서 `is_sunday` 매개변수 자체를 제거**하고 화답송 라벨 체크를 항상 수행하도록 단순화(§8.6에서 이미 승인한 방향과 일치) |

#### 8.3.1 구현 단계에서 발견된 설계 문서 오류 — `update_화답송` 호출부 부호 반전

이 문서(및 원본 설계서 `01_architect_design.md` §4.2)의 최초 버전은 `update_화답송(...,
is_sunday=use_weekday_display)`로 **그대로 대입**하라고 적었으나, 이는 실제 함수 구현
(`missa_content_updaters.py` `if not is_sunday: # 평일미사 포맷`)과 정반대 의미다 —
`is_sunday`는 "평일식 표시인가"가 아니라 "주일 포맷(악보 포함)인가"를 뜻한다. 그대로 대입하면
adult 주일미사가 텍스트만(평일 포맷)으로 생성되고 youth는 반대로 악보 포함 포맷이 되어버려
요구사항과 정반대 결과를 낳는다. 이 문서 §12(원본 테스트 목록 S4)는 애초에 "youth 경로에서
`is_sunday=False`가 호출되어 텍스트만 생성됨"이라고 **정확하게** 명시하고 있었으므로, 오류는
호출부 치환표 한 곳에만 있었다. `ppt-ooxml-specialist`가 실제 함수 코드와 테스트 스펙을 대조해
직접 발견·수정했다(재설계 왕복 없이 진행 — 판단의 여지가 없는 명백한 부호 오류였기 때문).

### 8.4 `find_files()` 매개변수 리네임 (리더 결정 — 부록 항목 3 승인)

`is_sunday` → `copy_hymn_scores`로 리네임한다. 내부 전용 함수(위치 인자로만 호출, 외부 공개
API 아님)라 breaking change 리스크가 낮고, 이름을 그대로 두면 다음 확장(어린이미사 등)에서
같은 암묵적 결합 실수가 재발할 위험이 크다는 아키텍트 분석에 동의한다.

### 8.5 `update_화답송()`/`validate()` 내부 매개변수명은 유지

두 함수는 내부에서 이미 "악보 포함 여부"라는 단일 의미로만 `is_sunday`를 쓴다(다른 축과 섞인
적 없음 — 문제는 `missa_to_ppt.py`의 호출부 변수가 여러 의미를 겸했던 것). 호출부에서
`use_weekday_display`라는 올바른 이름의 변수를 이 자리에 넘기기만 하면 충분하며, 함수
시그니처 자체를 바꿀 필요는 없다.

### 8.6 `validate()` 화답송 라벨 체크 (리더 결정 — 부록 항목 2 승인)

기존 `if is_sunday: check_kws.append('화답송')`(주일미사만 검증)를 **`mass_type`/표시형식
어디에도 묶지 않고 항상 체크**하도록 단순화한다. 화답송 라벨은 평일 포맷에서도 존재하므로
검증을 배제할 근거가 없고, 애매한 축을 ②(표시형식) 플래그에 얹으면 다섯 번째 암묵적 결합을
또 만드는 셈이다. 구현 단계에서 adult 회귀 테스트로 실제 영향 없음을 확인 후 반영.
