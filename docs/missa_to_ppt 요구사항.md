# 1부. 공통 요구사항

## 1.1 개요

한국천주교주교회의 매일미사 사이트(missa.cbck.or.kr)에서 날짜별 미사 내용을 가져와서, 이전
미사의 PPT 파일을 수정하여 새 미사 날짜의 PPT 파일을 만든다. 참조 PPT의 폰트·서식·레이아웃·
배경은 그대로 유지하고 텍스트와 슬라이드 구성만 교체하는 것이 이 프로그램의 핵심 원칙이며,
성인미사·청년미사 모두 이 원칙을 따른다.

미사 유형은 `--미사유형` CLI 플래그(`성인`/`청년`/`어린이`, 기본값 `성인`)로 정해진다.
**GUI는 미사 유형을 팝업으로 묻지 않는다** — 실행 아이콘·바로가기별로 유형이 미리 고정되어
있으면 사용자는 이 플래그를 의식할 필요가 없다(§1.7 참고). `어린이`를 주면 날짜 유무와 무관하게
"아직 지원하지 않는다"는 안내만 뜨고 조용히 종료한다(파이프라인 자체가 없음).

## 1.2 미사 유형 자동 판단과 4개 독립 축

- 입력 날짜가 일요일이면 주일미사, 아니면(토요일 포함) 평일미사로 자동 판단한다
  (`is_sunday_mass()`, 성인미사 한정 — 청년미사는 항상 토요일 입력이라 이 판단이 자연히
  거짓이 된다).
- "주일이냐 평일이냐" 하나의 불리언이 실제로는 서로 독립적인 4개 개념(①달력상 일요일 여부,
  ②화답송/미사후기도 등 표시 형식이 평일식인지, ③2차봉헌을 5종 성가에 포함하는지, ④성가 악보를
  실제로 복사하는지)을 겸하고 있었다는 것이 청년미사 확장 과정에서 드러났다. 청년미사는
  `(①거짓, ②③④ 모두 참)`이라는, 기존 주일(전부 참)도 평일(①②만 거짓)도 아닌 제3의
  조합을 요구하기 때문이다. 이에 따라 ②③④는 `mass_type`에서 직접 도출되며, 성인미사는
  4개 값 전부가 ①(또는 그 부정)에서만 파생되어 기존 동작과 100% 동일하게 유지된다.
- 토요일도 현재는 평일미사로 처리된다(성인미사 경로). 별도 로직이 필요해지면
  `is_sunday_mass()` 자체를 확장해야 하며, 이 변경의 회귀 기준점은
  `tests/test_missa_regression.py`의 `TestIsSundayMass.test_saturday_currently_treated_as_weekday`다.

## 1.3 오류 알림 / 로그

실행 중 오류가 발생하면(성가 번호/파일 누락 등) 팝업에는 해당 오류 메시지만 간결하게 표시한다.
처리 과정 전체 로그는 팝업에 늘어놓지 않고 `output/{출력 폴더}/log/`에 파일로 저장한다(GUI
경로에서만; CLI 직접 실행은 로그 파일을 만들지 않는다). 성인·청년 공통.

## 1.4 미사 JSON 공통 규칙

- `missa_to_json.py`가 missa.cbck.or.kr을 크롤링해 자동 생성한다. 이미 존재하면 재크롤링을
  생략한다.
- 섹션: 입당송, 제1독서, 화답송, 제2독서(있는 경우), 복음환호송, 복음, 영성체송.
- 독서·복음은 `title`(성서명)과 `chapter_verse`(장·절)를 분리해 저장하고, `content`는 절
  사이 개행을 제거해 하나의 문자열로 병합한다(절 번호는 본문 안에 유지). 화답송·입당송·
  영성체송의 `content`는 줄 구분(`\n`)을 유지한다.
- `extract_liturgy_name()`은 `<meta name="title">` 파싱에 더해, `<h3 id="missa_title"><sub>`
  부제(예: "(세계 이주민과 난민의 날)")가 있으면 공백 하나를 두고 덧붙인다.

## 1.5 독서·복음 본문 처리 (공통 알고리즘)

이 절의 알고리즘은 한글(성인미사 1·2독서, 복음)과 영문(청년미사 복음) 모두에 적용되는 공유
엔진이다. 언어별 폰트 메트릭 계산 방식만 다르고(§3.4 참고), 나머지 규칙은 동일하다.

- 본문 내 숫자(절 번호)는 오렌지색(RGB 255,192,0). 같은 절 내 `\n`은 무시하고 이어서 표시한다.
- 본문은 **슬라이드 단위로 정확히 채운다**(2026-10-03 구조 변경): 첫 슬라이드를 정확히 9줄(`LINES_PER_SLIDE`)로
  완성하고, 남은 본문으로 다음 슬라이드를 같은 방식으로 만든다. 따라서 **마지막 1장을 제외한 모든 본문 슬라이드는
  정확히 9줄**이고(문단이 슬라이드 경계에서 잘릴 때 앞 슬라이드 마지막 줄은 항상 꽉 찬 줄이라 짧은 꼬리 줄이
  생기지 않는다), 마지막 슬라이드는 남은 만큼(≤ 9줄)이다. 예외는 없다. 오버플로는 절대 허용하지 않는다.
- 줄 수와 절단 위치는 추정이 아니라 **실제 PowerPoint(COM)로 실측**한다: 남은 본문 앞부분을 현재 슬라이드의 실제
  본문 상자(같은 폭·글꼴·줄간격)에 임시로 놓고 줄 수와 줄 시작 위치를 얻어 10번째 줄 시작에서 자른다. 줄바꿈은
  단어 경계 word-wrap 기준이며 모든 템플릿이 한글도 단어 단위로 줄바꿈한다. PowerPoint COM을 쓸 수 없는
  환경(`config.json`의 `com_verification_enabled=false` 포함)에서는 같은 슬라이드 단위 루프를 Pillow word-wrap
  (실제 폰트 — TTC 파일 안 서체 인덱스를 직접 확인 — 와 한글 커닝 미지원 보정 `_RENDER_WIDTH_CALIBRATION`)로
  수행한다. Pillow는 PowerPoint와 줄 수가 어긋날 수 있으니 이 폴백 결과는 실측으로 확인하는 것이 맞다.
- 절 하나 = run 2개(절 번호+본문)라고 가정하지 않는다. continuation으로 여러 절이 하나의
  논리 단락에 병합된 경우 절 번호 run이 단락 중간에도 나타날 수 있으므로, 단락을 나누는
  로직은 분리 지점의 앞뒤 run 서식(오렌지색 포함)을 실제로 찾아 보존해야 한다.
- 종료 텍스트("주님의 말씀입니다." 등)는 본문과 별도 처리한다: 마지막 슬라이드 본문이 **실측** 5줄
  이하이면(마지막 슬라이드를 확정할 때 얻은 실측 줄 수로 판정 — 27자/줄 추정 사용 안 함) 같은 슬라이드에 통합하고, 1줄 높이는 본문 박스 높이÷9 역산이 아니라 실제 폰트
  크기·줄간격으로 계산한다. 종료 텍스트박스는 반드시 한 슬라이드에 온전히 담겨야 하며(분리
  금지), 안 들어가면 통째로 다음 슬라이드로 옮긴다. 제1독서·복음의 종료 위치는 제2독서
  종료 슬라이드를 기준으로 정렬한다. 모든 독서·복음 슬라이드의 배경(검정 도형)은 항상
  슬라이드 전체를 덮어야 한다.

## 1.6 슬라이드 복사·서식 보존 공통 규칙

- 화답송 악보, 성가, 시작기도, 미사후기도, 공지사항 등 다른 PPT에서 슬라이드를 그대로 복사해
  올 때, 원본과 참조 PPT의 슬라이드 크기(가로세로 비율)가 다르면 도형이 절대 좌표 그대로
  복사되어 확대/잘림이 생길 수 있다 — 크기 비율만큼 도형 위치·크기를 보정하고, 텍스트가
  잘리지 않도록 폰트 크기·단락 여백/들여쓰기도 같은 비율로 함께 축소한다.
- 슬라이드 복사 후 원본 배경(레이아웃/마스터 상속 포함)은 이미 정확히 복사되므로 임의로
  다시 덮어쓰지 않는다. 슬라이드를 복제할 때는 배경뿐 아니라 마스터 상속 요소 노출 여부를
  결정하는 `showMasterSp` 속성도 원본과 동일하게 맞춘다.

## 1.7 실행 아이콘·바로가기

미사 유형별로 2줄 배지 아이콘(예: "성인"/"PPT")을 가진 실행 바로가기 3종을 만들 수 있다
(`tools/build_shortcuts.py`, 배포 담당자 전용). 각 바로가기는 `--미사유형 성인`/`청년`/
`어린이` 인자로 고정 실행되므로, 사용자는 원하는 유형의 바로가기를 더블클릭하기만 하면 된다
(날짜 없이 실행되므로 곧바로 파일 선택 화면으로 들어간다).

처리가 시작되면 진행 창 맨 위에 "PowerPoint가 백그라운드에서 실행됩니다" 안내가 **5초 동안** 표시된
뒤 사라진다(줄 수를 정확히 확인하려고 PowerPoint를 실제로 띄우기 때문). 별도 확인 팝업은 없고(2026-10-03
폐지), 그 5초 동안에도 진행 메시지·진행률은 같은 창에 함께 표시된다. 이 PowerPoint 창은 작업표시줄에는
나타날 수 있지만, 지금 쓰고 있는 창의 포커스를 가져가지는 않는다(실측 확인됨).

## 1.8 검증

- **실행 시 자동 검증(`validate`)**: liturgy 텍스트 존재(오류), 입당송·영성체송·화답송 슬라이드
  존재(경고), 제1독서가 있으면 절 번호가 실제로 오렌지색 run으로 렌더링됐는지 절 번호 단위로
  대조(경고 — 텍스트만 남고 색상만 사라지는 경우도 잡아냄). 오류가 있으면 검증 실패, 경고는
  로그만 남기고 계속 진행한다.
- **PPTX 구조 검증**: 저장 직후 OOXML 구조 자체가 손상 없이 열리는지 확인한다.
- **회귀 테스트**: `pytest tests/test_missa_regression.py tests/test_ppt_com_verify.py -v`.
  새 미사 유형/기능 추가 시 관련 케이스를 추가하고 회귀 없음을 확인한 뒤 병합한다. 테스트
  정책과 스위트 구성은 `docs/missa_to_ppt 구현 계획.md` §7(검증)을 참고.

## 1.9 첫 화면 '찾아보기' 시작 폴더와 결과창 '원드라이브로 복사' (2026-10-03, 성인·청년 공통)

로컬 'PPT 문서' 폴더(`config.json`의 `onedrive_ppt_folder`, 성인은 §2.1(C)·청년은 §3.3.1에서 1회 설정)를
알고 있으면 첫 입력 화면 각 행의 '찾아보기'가 아래 폴더에서 시작한다(`{PPT}` = 'PPT 문서'). 폴더 이름은 공백
유무 차이를 무시하고 찾으며, 하위 폴더가 없으면 있는 곳까지(최악엔 `{PPT}` 자체)만 내려간다.

| 행 | 시작 폴더 |
|---|---|
| 시작기도 PPT, 미사 후 기도 PPT (성인·청년) | `{PPT}/13.기도문` |
| 공지사항 PPT (성인·청년) | `{PPT}/11.공지사항 PPT문서` |
| 참조 미사 PPT (성인) | `{PPT}/10.기타 PPT문서/PPT 자동화/1.Template` |
| 참조 미사 PPT (청년) | `{PPT}/20.청년 미사/1.Template` |
| 화답송 악보 PPT/사진 (성인만) | 최초에는 `{PPT}`, 이후 직전에 고른 화답송 파일의 폴더(`config.json`의 `last_psalm_dir`; 폴더가 사라졌으면 `{PPT}`) |

청년 로그인(폴백) 방식의 OneDrive 브라우저도 같은 폴더가 펼쳐진 채로 시작한다(화답송 행 없음).

**결과창 '원드라이브로 복사' 버튼**: 처리가 끝난 결과 창에는 [파일 열기][원드라이브로 복사][폴더 열기][닫기] 순서로 버튼이 한 줄에 있다(2026-10-04: '파일 열기' 바로 옆,
같은 글꼴 크기). 누르면 결과 PPT를 아래 폴더에 저장하고(연도 폴더가 없으면 생성) 저장된 폴더를
안내한다. 같은 이름의 파일이 이미 있으면 덮어쓸지 먼저 묻고, 실패하면 오류를 안내한다.

| 미사 | 저장 폴더 |
|---|---|
| 성인 | `{PPT}/{YYYY}/` (루트를 모르면 이때 'PPT 문서' 폴더 선택창을 띄움) |
| 청년 | `{PPT}/20.청년 미사/{YYYY}/` (로그인 방식이면 Graph로 같은 위치에 업로드) |

YYYY는 사용자가 입력한 날짜의 연도다. 결과 PPT 자체는 항상 `output/`에만 생성한다(§3.8).

# 2부. 성인미사 전용 요구사항

## 2.1 실행 방식

### (A) 대화형 모드 — `python missa_to_ppt.py` (또는 `--미사유형 성인`만, 날짜 없이)

팝업 순서: ① 미사 일자 입력 → ② 파일 선택 화면(참조 PPT 필수, 시작기도/화답송 악보 PPT 또는
사진/공지사항/미사후기도 PPT는 선택 — 화답송은 주일미사에만 필요하며 미입력 시 경고 후 진행
확인, 공지사항은 `.pptx`만 허용; 확인 버튼 아래에 현재 버전과 "🔄 업데이트 확인" 링크가
표시된다; '찾아보기' 시작 폴더는 §1.9) → ③ 성가번호 입력(입당·봉헌·성체·2차봉헌·파견 — 주일은 5종 전부, 평일은 2차봉헌
제외 4종 필수, 숫자 형식 검증) → ④ 처리 시작(진행 창, §1.7의 PowerPoint 안내 5초) → ⑤ 결과 창('원드라이브로 복사' 버튼, §1.9).

### (B) CLI 모드 — 날짜 포함 인수 지정

```
python missa_to_ppt.py YYYYMMDD [--입당 N --봉헌 N --성체 N --2차봉헌 N --파견 N]
  [--화답송 PATH] [--미사후기도 PATH] [--공지사항 PATH] [--test] [--미사유형 성인]
```

성가번호 생략 시 팝업 입력. `--test`는 팝업 없이 날짜 폴더 파일로 번호를 자동 추론한다(자동화
테스트용). 입력 파일은 `output/YYYYMMDD/`에서 자동 탐색하며 위 옵션으로 경로를 직접 지정할
수 있다. `--공지사항`은 `.pptx`만 허용(다른 확장자는 오류로 중단).

### (C) 성가 폴더 최초 설정

성인미사도 청년미사와 같은 방식으로 로컬 **'PPT 문서' 폴더**를 최초 1회 고른다(같은 설정 키
`onedrive_ppt_folder`; 그 안에 `09.가톨릭 성가` 폴더가 있어야 유효하며, 무효하면 안내 후 다시 묻고 취소하면 기존
방식으로 진행). 선택하면 `onedrive_hymn_folder`가 `{PPT}/09.가톨릭 성가/성가-악보버전`으로 함께 저장되어 성가 PPT는 그
폴더(또는 Graph API 미러링 캐시)에서 찾는다. 기존에 `onedrive_hymn_folder`가 유효한 PC는 그 폴더의 두 단계 위를
'PPT 문서'로 간주해 선택창을 다시 띄우지 않는다. 이 폴더로 §1.9의 '찾아보기' 시작 폴더와 결과 복사 위치를
정한다.

## 2.2 입력 파일

1. **참조 미사 PPT** — 날짜 폴더 안에서 파일명에 당일 날짜가 없는 `.pptx` 중 선택(성가/
   시작기도/화답송악보 제외). 대화형은 직접 선택(필수), CLI는 자동 탐색.
2. **화답송 악보 PPT 또는 사진** — 대화형/CLI 모두 지원. 사진(PNG/JPG) 입력 시
   `missa_psalm_score_image.render_화답송_score_slide()`가 사진 한 장으로부터 악보 슬라이드를
   자동 생성한다(§2.4 참고). 평일미사는 사용하지 않음.
3. **시작기도 PPT** — 선택. 파일명에 "시작기도" 포함 시 자동 탐색.
4. **미사 후 기도 PPT** — 평일미사 전용. 파일명에 "미사후기도" 포함 시 자동 탐색.
5. **공지사항 PPT** — 선택. 지정하면 2차봉헌 성가 콘텐츠 바로 뒤에 원본 서식 그대로 삽입한다.
   2차봉헌 슬롯이 없는 미사는 경고 후 건너뜀. `.pptx`만 허용(확장자 검증).
6. **성가 PPT**(입당·봉헌·성체·2차봉헌·파견) — 주일미사는 OneDrive에서 자동 탐색(못 찾으면
   날짜 폴더 폴백) 후 원본 그대로 복사, 평일미사는 악보를 쓰지 않으므로 OneDrive를 조회하지
   않고 구분(divider) 슬라이드 번호만 갱신한다. **필수 악보 파일 검증**: 주일 5종/평일 4종 중
   실제 악보 파일을 못 찾으면 어떤 성가가 없는지 명시한 오류로 중단한다(번호 누락과는 별개로,
   번호는 있으나 파일이 없는 경우를 잡는다).
7. **미사 JSON** — §1.4 공통 규칙.

## 2.3 처리 및 출력

1. `missa_to_json.py` 실행(이미 있으면 생략) → 2. 전례 텍스트 교체(제목·입당송·1독서·2독서·
복음환호송·복음·영성체송) → 3. 시작기도문 교체(지정 시) → 4. 성가 슬라이드 처리(5종) →
5. 검증 → 6. `output/YYYYMMDD/{liturgy}.pptx` 저장. 공지사항은 지정 시 2차봉헌 콘텐츠 뒤에
삽입.

- **주일 추가 처리**: 화답송 악보 슬라이드 복사 + 텍스트 슬라이드 배치.
- **평일 추가 처리**: 화답송 텍스트 슬라이드만 배치(악보 없음), 파견성가 다음에 미사후기도
  삽입(지정 시).

## 2.4 세부 요구사항

**제목 슬라이드**: 날짜(연·월·일)와 전례명(liturgy) 교체, 기존 포맷 유지.

**입당송**: content 앞에 "◎ \t" 추가, 기존 들여쓰기·탭 정렬 유지.

**제1독서**: 제목 슬라이드는 성서명만(절 번호 제거), 본문 슬라이드는 §1.5 공통 규칙.

**화답송**:
- 주일: [악보]-[절1]-[악보]-[절2]-... 교대 배치. 악보 슬라이드는 화답송 악보 PPT에서 원본
  서식 그대로 복사(§1.6). 화답송 악보 PPT가 없고 원본 사진만 있으면
  `render_화답송_score_slide()`가 대신 악보 슬라이드를 만든다: (1) 사진 좌측 "화답송" 워터마크를
  워터마크-오선보 사이 완전 공백 띠로 자동 크롭(못 찾으면 크롭 생략+경고), (2) 오선 전체를
  관통하는 마디 경계(바 라인)를 탐지하되 온음표·8분음표 기둥+깃발 등 오검출은 인접 잉크 지속
  여부로 배제, (3) 이미지 중앙 30~70% 구간에서 좌우 폭이 가장 균형 잡힌 지점을 분할점으로
  선택해 상/하 2단으로 나눔(무손실), (4) 상단 왼쪽 정렬·하단 오른쪽 정렬로 고정 템플릿
  (`assets/화답송_악보_template.pptx`)에 배치하며 두 단에 **공통 배율**을 적용(더 제약이 큰
  쪽 기준, 음표 크기 통일), (5) 제목만 JSON `화답송.title`로 교체하고 나머지 고정 요소는
  보존. 텍스트 슬라이드는 절 내용만(`○ \t` + 내용, 후렴 제외 — 후렴은 악보 슬라이드에 포함).
- 평일: 텍스트 슬라이드만(후렴 ◎도 텍스트로 표시, 악보가 없어 표시할 곳이 텍스트뿐이므로).
  참조 PPT의 화답송 텍스트 템플릿을 `find_sections()`로 동적 탐지해 복제한다.

**제2독서**: 제목은 성서명만, 본문은 §1.5 공통 규칙. JSON이 null이면 슬라이드 전체(직전 blank
포함) 삭제. 평일에도 대축일 등에서 있을 수 있다.

**복음환호송**: 본문 교체, run-level 서식 보존(◎ 알렐루야 줄과 ○ 구절 줄의 서식이 다름).

**복음**: 제목은 복음사가 이름+조사, 본문은 §1.5 공통 규칙.

**영성체송**: 본문 교체.

**성가 처리**(순서: 입당→봉헌→성체→2차봉헌→파견): 주일은 원본 양식 그대로 복사(악보 포함) +
타입/번호 갱신. 원본 악보 첫 줄의 구분 라벨(예: "2차 봉헌")이 이번 주 실제 용도와 다르면 번호와
함께 라벨도 교정한다(찾지 못하면 경고만, 처리는 계속). 라벨/번호 글자 수가 바뀌어도 각 글자의
원본 색상은 유지되어야 한다. 평일은 구분 슬라이드만 갱신, 악보는 복사하지 않고 기존 악보
슬라이드는 삭제한다.

**미사 후 기도**(평일 전용): 파견성가 다음(파견 콘텐츠 → blank → 미사후기도 → blank → 파견
순서 참조)에 원본 서식 그대로 삽입. 파일 미지정 시 생략(오류 아님, 기존 슬라이드가 있으면
보존).

**공지사항 삽입**: `sections['2차봉헌_content_end']`(기존 blank)를 앞 구분선으로 재사용하고,
콘텐츠 뒤에 새 구분 슬라이드 1장만 추가한다. 2차봉헌 슬롯 없음/로드 실패/0장은 경고 후 건너뜀
(예외로 중단하지 않음).

# 3부. 청년미사 전용 요구사항

청년미사(토요일 저녁)는 2단계로 나눠 진행됐다 — 1단계(영문 복음 조회·PDF 성가집→PPT, 독립
leaf 모듈)와 2단계(배포 전환·OneDrive 인증·전체 파이프라인 통합). 두 단계 모두 **완료**됐다.
아래는 현재 유효한 요구사항만 압축해 정리한 것이며, 각 항목이 왜 그렇게 결정됐는지(실측 근거,
발견된 버그와 수정 경위)는 `docs/missa_to_ppt 요구사항 변경이력.md`와
`docs/missa_to_ppt 구현 계획.md` 3부를 참고.

## 3.1 배포 방식

- 웹 인터페이스는 기각, **로컬 실행 + GitHub 자동 업데이트**로 확정. GitHub 저장소는 public
  전환 완료(비밀값 없음을 확인 후 진행).
- 업데이트는 앱 실행 시 자동이 아니라 "업데이트 확인" 버튼을 눌렀을 때만(`missa_updater.py`,
  GitHub commit SHA 비교 → zip 다운로드 → `*.py`/`*.spec`/`VERSION`/`assets/` 화이트리스트만
  교체, `config.json`/`output/`/`reference/`/`cache/`/`.git/`은 절대 덮어쓰지 않음).

> **참고(2026-10-02)**: 아래 §3.3·§3.4의 Graph 로그인/브라우저/온디맨드 조회 서술은 §3.3.1의
> **폴백 모드** 동작이다. 기본(로컬 모드)은 §3.3.1을 따른다.

## 3.2 초기 입력 화면과 미사 유형 분기

- 미사 유형은 `--미사유형` CLI 플래그로 미리 정해지며(§1.1), GUI가 팝업으로 다시 묻지 않는다.
  청년을 선택하면 입력 화면에 성가 출처 4종 선택, 성체성가 2곡 입력, 영문 복음 관련 청년
  전용 옵션만 노출되고(화답송 악보 입력 행은 숨김 — 청년은 화답송 악보를 쓰지 않음), 성인은
  기존 화면 그대로다.
- 확장 가능 구조: `MASS_TYPE_OUTPUT_SUFFIX`/`MASS_TYPES` 류의 매핑에 유형을 추가하는 것만으로
  향후 어린이미사 등을 확장할 수 있게 설계되어 있다(실제 어린이미사 UI 구현은 범위 밖).

## 3.3 OneDrive 연동

- **인증**: 성당 공용 Microsoft 365 계정 1개(개인별 로그인 없음). Microsoft Graph API,
  **Device Code Flow**(MSAL Python) — 퍼블릭 클라이언트로 Azure AD 등록(client secret 불필요).
  스코프 `Files.ReadWrite`(MSAL이 `offline_access` 등을 자동 추가). 토큰 캐시
  (`msal_token_cache.bin`, `.gitignore` 등록)로 재로그인을 최소화한다.
  - 최초 로그인 시 기기 코드 화면이 뜨고, 사용자가 `microsoft.com/devicelogin`에서 공용
    계정으로 로그인한다. 이메일 인증 코드 확인 단계는 Microsoft 자체의 계정 보호 절차라
    앱에서 비활성화할 수 없다. 코드 표시 창의 링크는 드래그 선택(복사)이 가능한 위젯으로
    표시된다(단일 클릭은 브라우저를 열고, 드래그 선택 중에는 열리지 않음).
  - 로그인 브라우저가 이미 다른 개인 계정으로 로그인돼 있으면 그 계정으로 진행될 수 있다 —
    앱이 계정을 강제할 수 없으므로(기기 코드 로그인 URL은 계정 힌트를 못 받는 고정 페이지),
    **새 시크릿/InPrivate 창**에서 로그인하도록 안내한다(`README_청년미사_운영자.md` 참고).
- **`missa_onedrive.py`**(신규 leaf 모듈): `get_access_token`/`list_children`/`download_file`/
  `upload_file`/`ensure_folder`/`get_item_metadata`. 앱 인스턴스는 프로세스 수명 동안 1회만
  생성해 재사용한다(매번 새로 만들면 생성 자체가 ~1초 걸림).
  - **주의**: 성당 공용 계정의 OneDrive에서 최상위 경로 `PPT 문서`는 진짜 폴더가 아니라 다른
    드라이브를 가리키는 **공유 바로가기(remoteItem)**다. 경로 기반 주소(`root:/PPT 문서/...:`)는
    이 바로가기를 통과하지 못해 하위 경로 조회가 실패한다 — 첫 세그먼트가 remoteItem인지 실제
    GET으로 확인해 캐시하고, 맞으면 `/drives/{driveId}/items/{itemId}/...` 주소로 전환해야
    한다.
- **`config.json` 스키마**: 기존 로컬 절대경로 키(`onedrive_hymn_folder`,
  `onedrive_youth_hymn_folder`)와 신규 원격 상대경로 키(`onedrive_hymn_path`,
  `onedrive_youth_hymn_path`)가 공존한다. **청년미사는 2026-10-02 요구사항(§3.3.1)부터 신규 키
  `onedrive_ppt_folder`(로컬 'PPT 문서' 폴더) 하나로 로컬/폴백을 판정**하며, 위 4개 키 중
  `onedrive_youth_hymn_folder`는 청년미사에서 더 이상 읽지 않는다(성인미사는 `onedrive_hymn_folder`
  를 기존대로 사용). 원격 상대경로 키(`onedrive_hymn_path`/`onedrive_youth_hymn_path`)는 폴백
  모드에서만 쓰인다.

## 3.3.1 청년미사 OneDrive 접속 모드 — 로컬 폴더 우선, 로그인 폴백 (2026-10-02 확정·구현 완료)

**배경**: 성인미사는 사용자가 지정한 로컬 OneDrive 동기화 폴더를 그대로 읽는데, 청년미사는
항상 Graph API 로그인(기기 코드)을 거쳐 PC마다 로그인이 필요하고 파일 하나당 네트워크 왕복
(호출당 약 3초)이 쌓여 느리다. 성인미사와 같이 **로컬 폴더 경로를 직접 지정하는 방식을 1순위**로
하고, 로그인 방식(§3.3·§3.4)은 폴백으로 남긴다. 성인미사 동작은 바뀌지 않는다.

**접속 모드 판정(실행 시작 시 1회, 단일 지점)**

| 조건 | 모드 | 동작 |
|---|---|---|
| `config.json`의 `onedrive_ppt_folder`가 존재하는 폴더이고 그 안에 `20.청년 미사` 폴더가 있음 | **로컬 모드** | OneDrive 로그인·Graph API·프리페치 스레드·전용 브라우저를 전혀 쓰지 않음 |
| 키가 없거나, 값이 가리키는 폴더가 없거나, 폴더는 있는데 `20.청년 미사`가 없음(삭제·이동·동기화 해제 등 어떤 이유든) | 선택창 표시 | 폴더 선택창을 띄워 사용자가 'PPT 문서' 폴더를 고르면 검증 후 `config.json`에 저장하고 로컬 모드로 진행 |
| 선택창에서 취소(또는 검증 실패 후 재선택 창에서 취소) | **폴백 모드** | 이번 실행은 기존 방식(기기 코드 로그인 → Graph API)으로 진행. 설정은 저장하지 않으므로 다음 실행에 선택창이 다시 뜬다 |

- **폴더 검증은 선택 직후와 매 실행 시작 시 모두 한다**: 선택한 폴더(또는 저장된 폴더) 안에
  `20.청년 미사` 폴더가 있어야 유효하다. 선택 직후 검증에 실패하면 경고를 띄우고 다시 선택하게
  하며, 재선택 창에서 취소하면 폴백 모드로 간다. 저장된 값은 `config.json`의 `onedrive_ppt_folder`
  (로컬 절대경로 문자열, 성인미사의 `onedrive_hymn_folder`와 별개)이고, 하위 경로는 저장하지 않고
  실행 때마다 조합한다.

- 사용자에게는 **'PPT 문서'(성당 PPT 문서) 폴더 하나만** 입력받는다. 하위 경로는 코드가 아래
  규칙으로 조합한다. 선택창 안내 문구에 "'PPT 문서' 폴더를 선택하세요. 설정하지 않고 취소하면
  OneDrive 로그인 방식으로 진행합니다"를 명시한다.
- 같은 실행 안에서 모드 판단을 여러 곳에서 따로 하지 않는다 — 시작 시 결정한 모드를 모든 단계(파일
  선택·성가 조회·결과 저장)가 공유한다(판단이 갈라지면 한쪽은 로컬, 한쪽은 Graph를 타 로그인 창이
  뒤늦게 뜨는 문제가 생긴다).

**로컬 모드의 하위 경로 규칙** (`{PPT}` = 사용자가 입력한 'PPT 문서' 폴더)

| 용도 | 경로 |
|---|---|
| 가톨릭성가 | `{PPT}/09.가톨릭 성가/성가-악보버전` (현재 코드의 기본 경로 유지) |
| 나주노 성가 | `{PPT}/20.청년 미사/2.성가/나주노 성가` |
| 야훼이레 성가 | `{PPT}/20.청년 미사/2.성가/야훼이레 성가` |
| 결과 PPT | `output/`에만 생성한다. `{PPT}/20.청년 미사/{YYYY}/`로의 복사는 결과창 '원드라이브로 복사' 버튼으로만(§1.9, §3.8) |
| 참조 PPT·시작기도·미사후기도·공지사항 | 로컬 파일 선택창(성인미사와 동일한 방식), 시작 위치는 §1.9의 행별 폴더 |

- 실제 폴더명은 `2.성가`(점 뒤 공백 없음)다 — 요청서의 "2. 성가"는 이 폴더를 가리키는 것으로
  해석한다.
- 성가 PPT 조회는 위 로컬 폴더에서 곡 번호 패턴으로 직접 찾는다(§3.4(2)의 우선순위 중 로컬 캐시 →
  OneDrive 재귀 검색 대신 로컬 폴더 검색 하나). 나주노/야훼이레 곡이 폴더에 없으면 PDF에서 새로
  생성해 위 로컬 폴더(`2.성가/나주노 성가` 등)에 저장한다 — OneDrive 데스크톱 앱이 알아서
  동기화하므로 직접 업로드하지 않는다.
- 4개 파일(참조 PPT·시작기도·미사후기도·공지사항) 입력 행은 로컬 모드에서 OneDrive 브라우저
  대신 일반 파일 선택창을 쓴다. 기존 팝업의 읽기전용 입력칸·필수/선택 규칙·검증(공지사항은
  .pptx만 허용 등)은 그대로다.
- 결과 PPT는 `output/{YYYYMMDD}_youth/`에만 생성한다(2026-10-03 변경: 이전의 자동 복사·Graph 업로드는
  삭제). 운영자가 결과를 검증한 뒤 결과창 '원드라이브로 복사' 버튼(§1.9) 또는 수동으로 올린다.

**폴백 모드**: 현재 §3.3·§3.4의 동작 그대로(기기 코드 로그인, `README` 시크릿 창 안내 유지). 파일 브라우저는
§1.9의 행별 폴더가 펼쳐진 채로 시작하고, '원드라이브로 복사'는 Graph로 같은 위치(`PPT 문서/20.청년 미사/{YYYY}/`)에
업로드한다.

## 3.4 OneDrive 파일 획득 방식 — 두 가지 서로 다른 메커니즘

> **적용 범위**: 이 절의 메커니즘(Graph 브라우저·온디맨드 조회)은 §3.3.1의 **폴백 모드**에서만
> 쓰인다. 로컬 모드에서는 로컬 폴더/파일 선택창을 직접 쓴다.

청년미사가 OneDrive에서 받아오는 파일은 용도가 둘로 나뉘고, 각각 다른 메커니즘을 쓴다.

**(1) 그 주에만 존재하는 개별 파일**(참조 PPT·화답송·시작기도·공지사항·미사후기도) —
`missa_gui._ask_onedrive_file_browser_popup()`: Tkinter Treeview 기반 탐색 팝업. 트리
최상위는 `'11.공지사항 PPT문서'`/`'13. 기도문'`/`'20.청년 미사'` 3개 폴더로 제한되고, 하위
폴더는 폴더 확장(더블클릭 또는 확장 화살표 — 둘 다 `<<TreeviewOpen>>` 가상 이벤트로 통일
처리) 시 lazy-load된다. 팝업이 열리는 시점(입력창이 뜨는 즉시, 로그인/네트워크 상태와 무관하게
논블로킹)부터 3개 루트 폴더 아래 모든 하위 폴더/파일을 백그라운드 스레드로 재귀 프리페치해
캐시를 데운다. 선택한 파일은 공유 캐시 폴더(`onedrive_cache/`, 날짜 폴더와 별개)에 원본 1부를
보관하고, 매니페스트의 `lastModifiedDateTime`이 OneDrive 쪽과 **문자열 완전일치**할 때만
재다운로드를 스킵한다(신선도 판단은 항상 실시간 `get_item_metadata()` 조회를 거치며, 트리
표시용 프리페치 캐시는 절대 이 판단에 재사용하지 않는다 — 서로 다른 목적의 캐시 계층이므로).
파일 선택은 다운로드를 기다리지 않고 결정적 목적지 경로만 계산해 즉시 반환하며, 실제 다운로드는
generation 추적 백그라운드 스레드가 처리한다 — 같은 슬롯을 같은 파일명으로 재선택해도(매주
다른 폴더에서 같은 이름이 반복되는 정상 관례) 구세대의 느린 다운로드가 최신 선택을 덮어쓰지
못하도록 커밋은 락 안에서 generation을 재확인한 뒤에만 수행한다.

**(2) 나주노/야훼이레/가톨릭성가 성가 PPT**(§3.5) — `missa_gui.find_youth_onedrive_hymn_file()`:
곡 하나만 요청받아 찾는 온디맨드 조회(2026-09-27 도입, 폴더 전체 미러링 방식을 대체). 우선순위는
(1) 로컬 캐시(`cache/{cache_subdir}/`, 성가 PPT는 한 번 만들어지면 바뀌지 않으므로 재확인
없이 재사용) → (2) OneDrive를 재귀 검색(`list_children()`만, 다운로드 없이 메타데이터 조회만
하므로 저렴)해 매칭되는 파일 하나만 다운로드. 이전에는 `get_onedrive_hymn_folder()`/
`get_onedrive_youth_hymn_root()`가 폴더 전체를 미러링해(가톨릭성가 폴더 34곡 등) 그날 실제로
쓰는 5곡만 필요한데도 전부 내려받았다 — 성인미사의 `get_onedrive_hymn_folder()` 자체는 이
변경과 무관하게 계속 전체 미러링 방식 그대로다(`mass_type == 'adult'`로 좁혀진 호출부에서만
쓰임).

## 3.5 성가 시스템 — 5종 × 4출처

- 5개 타입(입당/봉헌/성체/2차봉헌/파견) × 출처(나주노/야훼이레/가톨릭성가/기타) 선택 + 번호
  또는 제목 입력. 성체만 최대 2곡(두 번째는 선택사항, 비우면 1곡만 처리).
- 출처별 동작:

  | 출처 | 번호 | 제목 | 자동생성 | 헤더 포맷 |
  |---|---|---|---|---|
  | 나주노 | 필수 | 선택(자동조회) | PDF에서 생성 | `{타입} 나주노 {번호} {제목}` |
  | 야훼이레 | 필수 | 선택(자동조회) | PDF에서 생성 | `{타입} 야훼이레 {번호} {제목}` |
  | 가톨릭성가 | 필수 | 선택(없으면 파일명에서 파싱) | 없음(기존 폴더 검색) | `{타입} {번호} {제목}` |
  | 기타 | 입력 안 함 | 필수 | 없음 | `{타입} {제목}` |

- 나주노/야훼이레: §3.4(2)로 기존 PPT를 찾고, 없으면 `missa_youth_hymn_pdf.build_hymn_pptx()`로
  PDF에서 새로 생성해 같은 캐시에 저장한다(다음부터 재사용). 캐시 적중 여부와 무관하게 매번
  헤더(라벨/번호/제목)는 이번 주 값으로 다시 갱신한다.
- 가톨릭성가: 성인미사와 같은 검색 로직 재사용, 헤더는 기존 `_update_성가_header()`가 처리.
- 기타: 실제 PPT 없음 — 타이틀 슬라이드 텍스트만 갱신하고, **가사 placeholder는 프로그램이
  채우지 않는다**(담당자 후속 수작업). 다만 그 htype의 템플릿 기본 콘텐츠가 실제 악보 그림으로
  채워져 있던 경우(예: 2차봉헌 슬롯)에는, 콘텐츠를 빈 placeholder 1장으로 강제 교체해 지난주
  그림이 남지 않게 한다("기타를 고르면 콘텐츠는 항상 빈 placeholder 상태가 된다"는 결과를
  보장).
- 성체 2곡: 구분 슬라이드 없이 첫 번째 곡 뒤에 바로 이어붙인다.

## 3.6 영문 복음 레이아웃

- 1·2독서와 화답송은 한글 그대로(+1일 조회, §3.7), **복음만 영문**으로 교체한다.
  `missa_youth_gospel.get_youth_mass(content_date_str)`(universalis.com 조회)의 결과를
  기존 한글 JSON의 `복음.content` 자리에 병합한다. `복음.title`은 한글 그대로 유지(인트로
  슬라이드는 한글).
- universalis.com 조회는 리다이렉트를 자동으로 따라가지 않는다 — 날짜 범위를 벗어나면
  3xx로 "오늘의 복음"이나 안내 페이지로 조용히 넘어갈 수 있으므로, 최종 경로가 요청한 날짜와
  다르면 무조건 에러로 처리한다.
- 페이지 분배는 §1.5 공통 엔진을 그대로 쓰되, 영문 가변폭 텍스트는 한글 전각 문자 수 기반
  상수(`CHARS_PER_LINE`) 추정이 아니라 실제 PowerPoint 줄바꿈 실측(폴백은 Pillow word-wrap)으로
  슬라이드 단위로 채운다. 분할과 검증은 **항상 같은 박스 폭**을 써야 한다 — 한쪽에만 안전 마진을 곱하면
  실제로 들어가는 단어까지 다음 슬라이드로 밀어내는 반대 방향 버그가 생긴다.
- 영문 콘텐츠는 중앙 정렬(템플릿 자체에는 정렬 속성이 없어 기본값은 좌측 정렬이므로 명시
  적용), 한글 복음 인트로/클로징 슬라이드는 그대로 보존된다.

## 3.7 결과 PPT — 성인과 다른 점

- **날짜 처리**: 사용자는 토요일 날짜를 입력한다. 미사 내용(독서·화답송·복음 등) 조회는
  내부적으로 +1일(일요일)로 자동 변환된다. 파일명·출력 폴더명은 사용자가 입력한 토요일
  날짜를 그대로 쓴다.
- **화답송**: 항상 평일식(텍스트 슬라이드만, 악보 없음). 텍스트 자체는 한글 그대로(복음만
  영문).
- **복음환호송**: 청년 템플릿의 가운데 슬라이드는 문단이 1개(○ 구절)뿐이라, 성인 템플릿의
  3문단(◎/○/◎) 전제를 그대로 적용하면 ◎ 줄이 ○ 구절 문단의 라벨을 물려받아 잘못
  렌더링된다 — 청년 경로는 ◎ 줄을 제외하고 ○ 구절만 렌더링한다.
- **미사 후 기도**: 항상 평일식 게이트를 타므로 포함된다(파일이 준비되어 있으면).
- **2차봉헌**: 항상 5종 성가에 포함된다(요일과 무관, 템플릿 구조상 항상 존재).

## 3.8 결과 저장 경로

- 로컬: `output/{YYYYMMDD}_youth/`(성인은 `output/{YYYYMMDD}/`, 접미사 매핑을 거쳐 향후
  어린이미사 `_children/`까지 확장 가능). 한글/영문 미사 JSON도 콘텐츠 조회일이 아니라 **이
  입력 날짜 기준 폴더** 바로 아래 저장된다(파일명 자체는 `missa_{콘텐츠조회일}.json`/
  `missa_en_{콘텐츠조회일}.json`으로 콘텐츠 캐시 식별자 유지).
- **OneDrive에는 자동으로 올리지 않는다**(2026-10-03 변경): 결과 PPT는 `output/`에만 생성되고, 이전의
  자동 복사·Graph 직접 업로드 로직은 삭제됐다. 운영자가 결과를 검증한 뒤 결과창의 '원드라이브로 복사'
  버튼(§1.9)으로 `{PPT}/20.청년 미사/{YYYY}/`에 저장하거나(로컬 모드는 파일 복사, 폴백 모드는 Graph
  업로드) 수동으로 올린다. 성가 PPT를 새로 만들었을 때의 OneDrive 저장(§3.3.1)은 이 변경과 무관하게 유지된다.
- 파일명: `토요일 저녁 청년 주일미사_{YYYYMMDD}_{liturgy}.pptx`.

## 3.9 범위에서 제외한 것

- 어린이미사 등 청년 외 신규 미사 유형의 실제 UI/로직(구조만 확장 가능하게 준비).
- 성인미사(기존 교중미사) 결과물의 OneDrive 저장 전환.
- Graph API 미러링 캐시(§3.4(2) 도입 이전 나주노/야훼이레 전체 미러링 방식)의 역방향
  업로드(로컬에서 새로 만든 성가 PPT를 그 캐시를 통해서 OneDrive로 되돌려쓰는 것)는 로컬
  동기화 폴더가 아닌 Graph 미러링 캐시로 동작하는 PC에서만 의미가 있던 기능이며, §3.4(2)
  전환 이후 이 경로 자체를 타는 일이 줄었다.
