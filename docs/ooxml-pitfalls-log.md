## 기존 요소 교체 시 append() 금지 (pPr 자식 순서)

OOXML은 각 요소의 자식 순서를 XML Schema sequence로 강제한다. 순서가 틀리면 PowerPoint가
"손상된 파일" 오류를 표시한다.

**`<a:pPr>` (CT_TextParagraphProperties) 자식 순서:**
```
lnSpc → spcBef → spcAft → buClr → buSz → buFont → bu* → tabLst → defRPr → extLst
```

**절대 금지: `pPr.append(element)`.** `append()`는 요소를 맨 끝에 추가하므로 `lnSpc`가
`spcAft` 뒤에 오게 된다. 반드시 `insert(0, element)` 또는 스키마 순서에 맞는 위치에
`insert`를 사용한다.

```python
# ❌ 틀린 방법
pPr.append(pptx_parse_xml('<a:lnSpc .../>'))

# ✅ 올바른 방법 (lnSpc는 pPr의 첫 번째 자식)
pPr.insert(0, pptx_parse_xml('<a:lnSpc .../>'))
```

**기존 요소 교체 시**는 `remove()` 후 `insert(0, new_element)`를 사용한다. `append()`로
재추가하지 않는다.

**발견 경위 (2026-07-14):**
`_set_reading_text`에서 `lnSpc`를 `append()`로 추가해 `spcAft` 뒤에 놓이게 됐다.
특정 참조 PPT(`spcAft`를 포함한 단락 서식)에서만 오류가 재현되어 원인 파악에 오랜 시간이 걸렸다.

## 이 원칙은 `<a:pPr>`뿐 아니라 순서 스키마를 가진 모든 요소에 적용된다

`append()` 금지 원칙을 "pPr에 요소를 추가할 때"로만 기억하면, 순서가 강제되는 **다른**
요소를 건드릴 때 같은 함정에 다시 걸린다. 예: `<a:p>` (CT_TextParagraph)의 자식 순서도
`pPr? → (run|br)* → endParaRPr?`로 강제된다. 단락에서 기존 run/br만 지우고 `endParaRPr`는
남긴 채 새 run을 `p.append(new_r)`로 추가하면, 실제 순서가 `pPr → endParaRPr → r`가 되어
run이 endParaRPr **뒤에** 오는 스키마 위반이 된다.

```python
# ❌ 틀린 방법 — endParaRPr가 이미 남아있는 <a:p>에 append
p.append(new_r)   # 결과: pPr, endParaRPr, r (스키마 위반)

# ✅ 올바른 방법 — endParaRPr가 있으면 그 앞에 삽입
eprp = p.find(qn('a:endParaRPr'))
if eprp is not None:
    eprp.addprevious(new_r)
else:
    p.append(new_r)  # endParaRPr가 없으면 맨 끝이 곧 올바른 위치
```

새로운 요소 타입을 다룰 때는 "pPr 자식 순서"라는 암기된 규칙을 그대로 대입하지 말고,
해당 요소의 OOXML 스키마 시퀀스를 확인한 뒤 `append()`가 마지막 자식(시퀀스상 옵션인
꼬리 요소, 예: `endParaRPr`, `extLst`) 뒤에 요소를 놓지는 않는지 점검한다.

**발견 경위 (2026-08-29):** `missa_psalm_score_image.py`의 `_replace_title_paragraph`가
제목 단락의 run/br만 지우고 `endParaRPr`는 남긴 뒤 새 run을 `append()`해, `pPr → endParaRPr →
r` 순서로 렌더링됐다. `validate_pptx_structure()`(XML 제어문자·끊어진 rId만 검사)와 42개
프로그레션 테스트 전부가 이 스키마 위반을 잡지 못했고, 독립 코드 리뷰(`ooxml-code-reviewer`)가
실제 렌더링 XML을 직접 열어보고서야 발견했다. 구현자 본인은 "pPr을 직접 조작하지 않았으니
안전하다"고 자평했으나, append 위험을 "pPr 자식 순서"라는 기억된 형태로만 점검해 같은 원리가
`<a:p>` 자식 레벨(run vs endParaRPr)에도 적용됨을 일반화하지 못했다.

## 슬라이드 복사 시 배경/서식 재설정 금지

`copy_slide_from_prs()`는 원본 슬라이드의 배경(레이아웃/마스터 상속분까지 해석한 실제
배경)을 이미 정확히 복사한다. 복사 직후 `_set_slide_bg_black()`을 또 호출하면 방금
복사한 원본 서식을 하드코딩된 검정으로 덮어써 버린다. 다른 프레젠테이션에서 슬라이드를
복사해 온 경우(`copy_slide_from_prs`)에는 배경을 다시 강제하지 않는다. 같은 프레젠테이션
내부 템플릿을 복제한 경우(`insert_slide_copy`/`duplicate_slide`)는 원본이 이미 이 문서의
스타일을 따르므로 `_set_slide_bg_black()`을 걸어도 안전하다.

**발견 경위 (2026-07-16):** `update_화답송()`의 악보 슬라이드 분기에서 `copy_slide_from_prs()`
직후 `_set_slide_bg_black()`을 호출해 원본 화답송 악보 PPT의 서식이 사라졌다.

## 슬라이드 복제 시 `<p:sld>`의 `showMasterSp` 속성도 원본과 맞춘다

슬라이드를 복제할 때(`duplicate_slide`/`insert_slide_copy`)는 `p:cSld` 안의
`p:bg`(배경)뿐 아니라 최상위 `<p:sld>` 요소 자체의 `showMasterSp` 속성도 원본과 동일하게
맞춰야 한다. `showMasterSp="0"`은 슬라이드 마스터에 배치된 요소(배경 장식·로고 등)를 이
슬라이드에서 숨기라는 뜻으로, `p:bg`와는 **별개의** 속성이다 — 두 슬라이드가 같은
layout/master를 쓰고 `p:bg`가 동일해도, 한쪽에만 `showMasterSp="0"`이 있으면 마스터
상속 요소의 노출 여부가 달라져 색이 다르게 보인다.

`python-pptx`의 `prs.slides.add_slide()`가 만드는 새 슬라이드의 `<p:sld>`에는 이 속성이
아예 없다(속성 부재 = 기본값 "마스터 요소 노출"). 따라서 복제 시 원본의 값을 명시적으로
옮겨야 한다. `showMasterSp`는 `p:sld`의 네임스페이스 프리픽스 없는 unqualified
attribute이므로 `qn()` 없이 `src_slide.element.get('showMasterSp')` /
`new_slide.element.set('showMasterSp', ...)`로 처리한다(자식 요소 조작이 아니라 요소
자체의 속성이라 순서 스키마 함정과는 무관). 원본에 속성이 없으면 새 슬라이드에도 넣지
않는다(불필요한 속성 주입 금지).

향후 빈 슬라이드를 삽입할 때도 이 원칙이 그대로 적용된다 — 새 blank 슬라이드를 어떤
원본에서 복제하든, 원본의 `showMasterSp` 상태를 따라가야 마스터 상속 요소의 노출이
원본과 일치한다.

**발견 경위 (2026-09-13):** 실사용자가 2026-09-13 실제 미사 PPT(`20260913_연중 제24주일.pptx`)를
생성해 육안 검수하던 중, `insert_공지사항()`이 만든 뒤쪽 구분 슬라이드(1-based 142)가 앞쪽 구분
슬라이드(1-based 133, `2차봉헌_content_end`를 재사용한 hand-authored 슬라이드)와 색이 달라 보이는
것을 발견했다. 두 슬라이드는 `slide_layout`이 완전히 동일한 객체이고 둘 다 자체 `p:bg`가 없어
배경 속성은 100% 동일했으나, raw XML을 직접 비교하니 앞쪽은 `<p:sld showMasterSp="0">`인데 뒤쪽은
이 속성이 아예 없었다(python-pptx `add_slide()` 기본값). 뒤쪽 슬라이드는 마스터 상속 요소 숨김이
적용되지 않아 마스터 요소가 그대로 노출돼 색이 달라 보였다. 근본 원인은 `missa_ooxml_utils.py`의
`duplicate_slide()`가 `_copy_spTree`·`_copy_image_rels`·`p:bg` 복사는 하면서 최상위 `<p:sld>`의
`showMasterSp` 속성은 복사하지 않던 것이었다. 이 속성을 원본과 동일하게 설정하도록 고쳤다.

## 같은 프레젠테이션 내부 복제는 "빈 레이아웃 이름 검색"이 아니라 원본 레이아웃을 그대로 재사용

**발견 경위 (2026-09-24):** 청년미사 확장 B/A/C/D 라운드(C1) 작업 중, 나주노 151번 성가의
저작권 표시 미검출 버그를 조사하다 별개 증상을 하나 더 발견했다 — 151번 성가로 빌드한
결과물을 실측하니 슬라이드 14('빈 화면' 레이아웃)와 15~17('Blank' 레이아웃)이 서로 다른
레이아웃을 쓰고 있어 배경/서식이 미세하게 갈라져 보였다. 원인은 `missa_youth_hymn_pdf.py`의
`duplicate_slide()`(청년미사 성가 슬라이드를 곡 내에서 여러 장 복제할 때 씀)가 매번
`_blank_layout(prs)`를 호출했던 것이다. 이 헬퍼는 `prs.slide_layouts`를 순회하며 이름이
'Blank'/'빈 화면'/'blank'인 첫 레이아웃을 반환하는데, 청년미사 성가 템플릿
(`assets/청년미사_성가_template.pptx`)은 원본 슬라이드가 '빈 화면' 레이아웃을 쓰지만
`slide_layouts` 목록 자체에는 'Blank'가 '빈 화면'보다 먼저 등장한다. 그래서 매번 다른
레이아웃이 아니라 매번 **같은(첫 매칭)** 'Blank'가 선택됐고, 결과적으로 원본(14번, '빈
화면')과 복제본(15~17번, 'Blank')의 레이아웃이 갈라졌다.

`duplicate_slide()`는 **같은** 프레젠테이션 안에서 복제하므로 `src_slide.slide_layout`이
항상 유효한 레이아웃 객체를 가리킨다 — `_blank_layout()`으로 "이름을 다시 검색"할 이유가
애초에 없었다. `_blank_layout()` 호출을 제거하고 `prs.slides.add_slide(src_slide.slide_layout)`
로 직접 원본 레이아웃 객체를 재사용하도록 고쳤다. `_blank_layout()` 자체는 삭제하지 않았다 —
`copy_slide_from_prs()`(**다른** 프레젠테이션에서 복사할 때, 소스 레이아웃 이름이 타겟에 없는
경우의 최후 폴백)에서는 여전히 정당한 용도로 쓰인다. "이름으로 레이아웃을 찾는" 방식 자체가
잘못된 게 아니라, **같은 프레젠테이션 내부 복제에 그 방식을 쓸 필요가 없는데도 썼다**는 게
문제였다.

CLAUDE.md "슬라이드 복사 시 배경/서식 재설정 금지" 원칙 계열의 새 사례로 볼 수 있다 —
`p:bg`/`showMasterSp`뿐 아니라 레이아웃 자체도 "이미 정답인 원본 값을 재사용하면 될 것을
별도 로직으로 다시 찾다가" 어긋난 경우다.

## 여러 곳에서 재사용하는 fit-보정 함수의 "추정 vs 실제" 안전 마진은 이미 실측된 보정치를 재사용한다

**발견 경위 (2026-09-24):** D3(청년미사 확장 B/A/C/D 라운드) — 실사용 산출물
(`output/20260919/...pptx`)을 실측해보니 '영성체송' 슬라이드의 본문 도형('직사각형 2')이
슬라이드 밖으로 넘쳤다. 이 도형에는 `<a:spAutoFit/>`(텍스트 분량에 맞춰 도형 높이가 자동으로
늘어남)이 걸려 있어, 실제 PowerPoint에서 문구가 길면 도형이 top을 고정한 채 아래로 자란다.
`update_영성체송()`은 이미 `_adjust_fit_if_needed()`(화답송·복음환호송과 공유하는 겹침 자동
조정 함수 — "성인 경로의 유사 로직 재사용"을 확인하려 조사했더니 정확히 이 함수가 그 로직
이었다)를 호출해 "추정 필요 높이 ≤ 전례문 텍스트까지 여유 공간"을 비교하고 있었지만, 실사용
영성체송 문구(char-count 근사 기준 5줄, 추정 높이 4064000 EMU)와 실제 여유 공간(4177044
EMU)의 차이가 2.7%뿐이라 조정이 트리거되지 않았다.

두 가지 대안을 검토했다. (1) Pillow 실측(`missa_reading_layout._rendered_wrap_count()` 재사용)
으로 `_estimate_text_lines()`(char-count 근사)를 대체 — 계산해보니 이 특정 문구에서는 Pillow
실측 줄 수(4줄)가 char-count 근사(5줄)보다 오히려 **적게** 나와(추정 높이가 더 작아짐) 이
사례의 오버플로를 못 잡는다는 게 드러나 폐기. (2) 안전 마진을 추정 높이에 곱한다 — 채택.
새 임의 값을 만드는 대신, 이 프로젝트에 이미 CLAUDE.md "한글 줄 수 계산: TTC 폰트 인덱스와
Pillow 커닝 한계" 항목으로 기록돼 있던 실측치("Pillow ascent+descent가 실제 PowerPoint 줄
높이보다 약 14~18% 작다")를 그대로 재사용해 `_FIT_HEIGHT_SAFETY_MARGIN = 1.15`(중간값)를
`_adjust_fit_if_needed()`의 모든 `est_h` 비교에 곱하도록 수정했다. 이 마진을 적용하면 실사용
사례가 정확히 (a) 줄간격 축소 단계(160%→100%)에서 잡혀, (b) 폰트 축소 단계까지는 가지 않는다
— 요구사항 문구("자동 줄간격 축소로 한 슬라이드에 맞춤")와 정확히 일치하는 결과였다.

**한계(정직하게 기록)**: 이 마진(1.15)은 새로 실측 검증한 값이 아니라 기존에 확립된 값을
재사용한 것이다. `_adjust_fit_if_needed()`가 쓰이는 화답송/복음환호송/영성체송 전체가 이제
이 마진의 영향을 받으므로, 성인 회귀 스위트 전체 통과로 "기존 케이스를 깨지 않음"은
확인했지만 "이 마진이 향후 모든 청년미사 영성체송/화답송 문구에 대해 항상 충분하다"는 것까지
보장하지는 않는다 — 더 근본적인 해결은 독서/복음 파이프라인처럼 PowerPoint COM 실측 검증
(`_count_slide_lines_verified` 계열)을 이 함수에도 도입하는 것이나, 이번 라운드 범위에서는
하지 않았다.

## 도형 분류 시 "빈 텍스트"가 falsy임을 주의

빈 문자열(`""`)은 파이썬에서 falsy다. 도형을 텍스트 키워드로 분류하는 코드(`'ending' if
kw in txt else 'content'` 같은 패턴)에서 `if key == 'content' and txt:` 식으로 "본문이
있는 content만 스킵" 조건을 걸면, 텍스트가 비어 있는 배경 도형(`BlackBg` 등)도 `content`

## 텍스트 키워드로 도형을 식별할 때 부분 문자열 충돌 주의

## 도형 위치 계산: 1줄 높이를 "박스 height ÷ 고정 줄 수"로 역산하지 않는다

텍스트박스의 1줄 높이가 필요할 때 `box.height // LINES_PER_SLIDE`(고정 줄 수로 나눔)로
역산하면 안 된다. 본문 박스 height는 슬라이드마다 다르고 "항상 그 줄 수만큼 꽉 차 있다"는
보장이 없다 — 줄 수가 적은(짧은) 슬라이드의 박스는 여전히 클 수 있어, 나눗셈이 실제보다
작은 1줄 높이를 만들어낸다. 1줄 높이는 실제 폰트 메트릭으로 직접 계산한다:
`_get_slide_render_params()`가 준 Pillow 폰트의 `getmetrics()`(ascent+descent, 96dpi px)를
EMU로 환산(1px=9525EMU)하고 lnSpc(spcPct) 배율을 곱한다(`_content_line_height_emu()`).
Pillow/폰트 미존재 시에만 기존 나눗셈으로 폴백한다.

**보정치 유도 상세:** Pillow의 ascent+descent는 PowerPoint 실제 줄 높이보다 약 14~18% 작다
(32pt BatangChe 실측: ascent+descent=44px → lnSpc 미적용 glyph 419,100 EMU, 실제 PowerPoint
단일 줄 ≈487,680 EMU(1.2×32pt) 이상 — 419,100/487,680 ≈ 0.86, 즉 약 14% 작음; lnSpc 110%를
한쪽에만 곱해 비교하면 최대 ~18%까지 벌어져 보일 수 있으므로 두 값에 항상 같은 조건(lnSpc
포함 여부)을 적용해 비교해야 한다). 겹침 방지 여백(GAP=2줄)이 이 과소추정을 흡수한다: 겹침
없음 조건은 `(line_count+GAP)×computed ≥ line_count×real`이고, 위 실측값을 대입하면
`419,100×(line_count+2) ≥ 487,680×line_count` → `line_count ≤ 12.2`. 즉 GAP=2면 본문 12줄까지
안전(병합 대상은 5줄 이하이므로 실무 마진 방대). lnSpc 배율은 computed·real 양쪽에 동일하게
곱해져 비율이 불변이므로 이 결론은 lnSpc 값과 무관하다.

**발견 경위 (2026-09-02):** `_reposition_merged_ending_shapes()`가 본문+종료 통합 슬라이드의
종료 텍스트박스 위치를 `line_height = content_shape.height // 9`로 계산했다. 20260906 제1독서
마지막 페이지(본문 5줄, 박스 height=2,876,621)에서 이 나눗셈이 실제보다 작은 line_height를
만들어 종료 텍스트박스가 본문과 약 640,000 EMU 겹쳤다. 줄 수 추정(`_wrap_line_count`)·검증
함수는 이 겹침을 잡지 못했고(줄 수는 정확했으므로), 실사용자 육안 검수로 발견됐다.

## 단락 분리·병합 함수는 run 개수를 2개로 가정하지 않는다

절 하나 = run 2개(오렌지 절 번호 + 흰색 본문)라고 가정하는 코드는 여러 절이 하나의 논리
단락으로 병합된 경우(`layout_units_on_slides()`의 `is_continuation` 병합) 깨진다. 이때
단락은 [오렌지][흰색][오렌지][흰색]... 처럼 run이 3개 이상이 된다. 단락을 두 조각으로
자르는 함수는 반드시 "분리 지점이 몇 번째 run의 몇 번째 글자인지"를 실제로 계산해서, 그
지점 앞뒤 run들의 서식(rPr)을 각각 그대로 유지해야 한다. `runs[0]`/`runs[1]`처럼 인덱스를
고정하거나 "마지막 run만 남기고 나머지 삭제" 같은 방식은 텍스트는 보존해도 중간 run의
색상(서식)을 조용히 잃어버린다 — 예외 없이 실행되므로 육안 검수 전까지 발견되지 않는다.
`_missing_orange_verse_numbers()`(§검증) 추가로 이런 사례를 자동으로 잡는다.

**발견 경위 (2026-07-26):** `_split_para_at_lines()`가 앞부분은 `runs[0]`(절 번호)+`runs[1]`
(본문)만 남기고 `runs[2:]`를 삭제, 뒷부분은 마지막 run만 남기고 나머지를 삭제하는 방식이었다.
51절과 52절이 continuation으로 병합된 단락(런: [51-오렌지][본문][52-오렌지][본문])이 슬라이드

## run별 텍스트를 재작성할 때 옛 run 길이로 통짜 재배치하지 말고 의미 단위 경계로 나눈다

여러 run에 걸친 앞부분 텍스트를 "run 서식은 보존하고 텍스트만 교체"하려고, 새 문자열을
옛 run의 글자 수만큼씩 순서대로 잘라 넣는 방식은 **길이가 바뀌면** 조용히 색을 오염시킨다.
새 텍스트가 옛 텍스트보다 길거나 짧으면 문자 위치가 통째로 밀리고, 원래 의미가 다른
구간(라벨 vs 구분자 vs 숫자)의 run 경계가 새 텍스트에서는 전혀 다른 위치로 이동한다. 그
결과 한 구간의 마지막 글자가 옆 구간의 run(우연히 다른 색일 수 있음)으로 밀려 그 색을
물려받는다. 이 코드는 예외를 던지지 않으므로 육안 검수 전까지 발견되지 않는다.

**규칙:** 여러 의미 구간(라벨·구분자·숫자처럼 색/역할이 다른 구간)에 걸친 텍스트를
재작성할 때는, 호출부가 이미 알고 있는 의미 경계(정규식 그룹 등)를 **재배치의 하드
경계**로 삼아 각 구간을 독립적으로 재배치한다. 한 구간의 길이 변화(증가/감소)는 그
구간이 점유한 run 안에서만 흡수되어야 하고, 다른 구간이 점유하던 run에 절대 닿으면
안 된다. `_update_prefix_in_runs()`는 `segments=[(old_text, new_text), ...]`를 받아
세그먼트별로 독립 재배치한다.

**발견 경위 (2026-09-02):** `_update_성가_header()`가 성가 456의 라벨 `2차봉헌`(4자)을
`CANONICAL_LABEL`로 `2차 봉헌`(5자, 공백 추가)으로 정규화하면서, `_update_prefix_in_runs()`가
라벨+구분자+숫자를 하나의 문자 스트림으로 통짜 재배치했다. 라벨이 1글자 늘어 문자 위치가 한 칸
밀리자, 라벨 마지막 글자 `헌`이 원래 구분자 공백 run(소스 제작자가 실수로 회색 bg2 lumMod75000
으로 칠해둔 run)의 슬롯으로 밀려 그 회색을 물려받아, 20260906 출력의 129~134쪽에서 `헌`만 회색

고쳐, 라벨 길이 변화가 숫자 쪽 run 색상을(또는 반대 방향으로) 침범하지 못하게 했다. 이는
"단락 분리·병합 함수는 run 개수를 2개로 가정하지 않는다"와 같은 계열의 함정이다 — "run 서식을
보존한다"는 목적은 같아도 "어느 run이 어느 새 글자를 받는가"의 배정 규칙이 부정확하면 색이
조용히 샌다.

## 이미지에서 여러 그룹을 크롭할 때는 전역 경계가 아니라 그룹별 경계를 쓴다

한 이미지(페이지 스캔본 등) 안에 여러 그룹(예: 악보 시스템 묶음)을 순서대로 잘라낼 때,
`detect_content_bounds()`류의 **전역** 좌우 경계를 모든 그룹에 공통으로 쓰면 안 된다. 그
이미지 안에 그룹과 무관한 다른 줄(제목·저작권 표기 등)이 그룹보다 더 넓게 뻗어 있으면,
전역 경계가 그 넓은 줄에 맞춰지고 모든 그룹의 크롭이 실제 내용보다 불필요하게 넓어져(그
그룹 우측에 흰 여백이 남아) 크롭이 "타이트하지 않게" 된다. 그룹별로 잘라야 하는 코드는
반드시 **그 그룹 자신의 행/열 범위 안에서만** 잉크(내용) 경계를 다시 계산해야 한다(예:
`_group_content_bbox(gray, group)` — 그룹의 top..bottom 행 범위 안의 잉크 열 min/max로
left/right 산출).

1차 수정(`_split_and_adjust_via_com()`만)을 적용해 재검증하니 `[9,9,6,4,2]` → `[9,9,9,1,2]`로

재검증") while 루프가 메인 루프와 별도로 구현돼 있었는데, `len(nxt_paras) <= 1: continue`로
**다음 슬라이드 단락이 1개뿐이면 애초에 흡수를 시도조차 하지 않는** 더 약한 버전이었기
때문이다 — 메인 루프가 만들어낸 개선이 이웃을 "단락 1개까지 소진된" 상태로 만들 때마다, 그
뒤를 이어받는 두 번째 루프가 그 상태를 방치했다.

최종 수정: 두 while 루프의 "미달 흡수" 로직을 `_try_absorb_underfull()` 헬퍼로 통합해 이
비대칭을 제거했다. 통합하면서 한 가지를 더 고쳤다 — 다음 슬라이드의 유일한 단락을 통째로
가져가도 넘치지 않는 경우, 기존 코드는 "다음 슬라이드가 완전히 비게 됨"을 이유로 **아무것도
하지 않았다**(그냥 `continue`). 이 가드의 원래 의도("빈 슬라이드가 결과물에 남으면 안 된다")는
정당하지만, 구현이 "아무것도 안 함"으로 그 의도를 지키려 한 게 문제였다 — 대신 통째로 흡수한
뒤 빈 슬라이드를 `delete_slide()`로 **삭제**하면 원래 의도(빈 슬라이드가 남지 않음)는 그대로
지키면서, 앞 슬라이드가 미달인 채로 고아가 되는 부작용도 없앨 수 있다. 최종 재현 결과:
`[9,9,6,4,2]` → `[9,9,9,2]`(콘텐츠 슬라이드 5장 → 4장으로 자연 수렴, 마지막 슬라이드만 미달).

이 삭제는 `n_content`/`_rebalance_reading_slides_post_write()`의 반환값(호출부가 종료 슬라이드
위치 계산에 쓰는 net 삽입 수)에 영향을 주므로, 삭제 시 두 값을 갱신하고 인덱스가 밀렸으니
`break`로 스윕을 재시작해야 한다(overflow 새 슬라이드 삽입 경로가 이미 쓰던 동일 패턴 재사용).
삭제 확정 전 COM 실측(`_count_slide_lines_verified`)으로 오버플로가 아님을 재확인한 뒤에만
삭제한다 — "삭제는 되돌릴 수 없는 조작"이므로 다른 분기(분리·이동)보다 보수적으로 다뤘다.

이 함수(`_split_and_adjust_via_com`)는 제1독서/제2독서/복음이 공유하므로 섹션 이름으로 분기하는
코드는 넣지 않았고, `label`은 로그 메시지에만 쓰인다. 독립 코드 리뷰(`ooxml-code-reviewer`)가
기존 유닛 테스트 5개 시나리오를 콜 순서·배치 결과까지 손으로 재추적해 회귀 없음을 확인했다
(상세: `_workspace/bugfix_제2독서_줄수_미달/02b_review_report.md`).

## Tkinter Treeview 등 GUI 위젯을 "펼치는" 방법이 여러 개일 때, 그중 하나에만 이벤트를 걸지 않는다

`ttk.Treeview` 같은 위젯에서 노드를 여는 방법은 하나가 아니다 — 행 텍스트 더블클릭과 확장
화살표(▶/▼ indicator) 단일 클릭은 서로 다른 이벤트고, 후자는 위젯이 자체 처리하는 네이티브
Tk 토글이라 앱 코드가 `<Double-1>`만 바인딩해두면 이 경로에서는 전혀 호출되지 않는다.
lazy-load처럼 "노드가 열릴 때" 반드시 실행돼야 하는 로직을 물리 트리거별로 따로 잡으면, 놓친
트리거 경로는 화면상 펼침 아이콘만 바뀌고 실제 데이터 로드는 영원히 일어나지 않는다 —
예외가 나지 않으므로 그 트리거를 직접 써보기 전까지는 발견되지 않는다.

## 표시 문자열과 실제 처리값은 반드시 분리한다

Tkinter `Entry`의 `textvariable`처럼, "보여주는 문자열"과 위젯이 실제로 들고 있는 "값"이
같은 변수를 공유하는 위젯에서, 그 값을 사용자 친화적으로 다듬어 보여주고 싶다는 이유로
변수 자체에 다듬은 문자열을 넣으면 안 된다 — 다른 코드가 나중에 그 변수를 읽어 실제
처리(파일 열기 등)에 쓰면, 다듬어진 문자열은 대개 더 이상 유효한 경로/식별자가 아니라서
존재하지 않는 값을 그대로 쓰게 된다. 예외가 나지 않고 화면상 표시가 그럴듯해 보이므로
늦게 발견된다. 해결책은 표시 전용 값과 실제 처리값을 처음부터 분리하고, 실제 처리값을
읽는 모든 지점이 "실제 처리값이 있으면 우선, 없으면 기존 표시값(호환)"을 강제하는 단일
헬퍼를 거치게 하는 것이다.

**발견 경위 (2026-09-26):** `missa_gui._ask_combined_input_popup(mass_type='youth')`에서
OneDrive로 고른 파일의 로컬 다운로드 경로(`output\{date}_youth\{파일명}`)가 46자 폭
Entry에 그대로 표시돼, 모든 청년미사 파일에 공통인 접두사 때문에 정작 파일을 구분하는
부분(파일명)이 잘려서 안 보였다(실사용자 스크린샷 — 참조 미사 PPT 입력창에
`output₩20260926_youth₩Template_토요일 저녁 청년...`까지만 보이고 파일명이 안 보임).
사용자 확인을 거친 요구사항대로 표시를 `PPT 문서/` 접두사를 뺀 OneDrive 상대경로로
바꾸려 했는데, Entry의 `textvariable`이 곧 `on_ok()`가 최종적으로 읽는 `vars_[key]`라서
그 변수 자체를 상대경로 문자열로 바꾸면 `on_ok()`가 존재하지 않는 경로("13. 기도문\위령
성월 기도.pptx"는 실제 파일시스템 경로가 아님)를 그대로 파일 복사/처리에 넘기는 회귀가
생길 뻔했다.

`_onedrive_display_path()`(표시 문자열 생성, `_ONEDRIVE_BROWSER_ROOT` 상수 재사용),
`_resolved_field_value()`(on_ok()의 5개 필드 조회 전부가 거치는 단일 지점 — 별도 dict
`_od_real_paths`에 실제 로컬 경로가 있으면 그걸 우선), `_apply_onedrive_selection()`
(`_browse()`가 해야 하는 실제 경로 저장·표시 문자열 설정·Entry `xview_moveto(1.0)` 스크롤
3가지 부작용을 한 곳에 모음) 3개 함수로 분리해 해결했다 — 셋 다 GUI 없이 순수/duck-typed
단위 테스트가 가능하다(상세: `_workspace/02_specialist_impl_notes.md` "I그룹" 절).

## Tkinter 합성 클릭 이벤트(`event_generate`)는 좌표와 `update_idletasks()` 없이는 조용히 무시될 수 있다

**발견 경위 (2026-09-26, §J그룹 배치7/J10):** '업데이트 확인'을 `tk.Button`에서
`tk.Label(cursor='hand2')` + `<Button-1>` bind로 바꾼 뒤(§J10), 실제로 클릭했을 때
`_on_check_update()`가 호출되는지까지 검증하는 `test_j10e_clicking_update_link_actually_
invokes_on_check_update`를 작성했다. 위젯을 찾아 `target.event_generate('<Button-1>')`
(좌표 없이)만 호출했는데, 구현이 명백히 맞는데도(육안 검수로도 클릭이 잘 됨) 이 테스트만
계속 실패했다.

먼저 문제를 프로젝트 코드와 완전히 분리해서 확인하기 위해, 별도의 5줄짜리 최소 재현
스크립트(새 `tk.Tk()` 창 하나 + `tk.Label` 하나 + `bind('<Button-1>', ...)` 하나만 있는
스크립트)를 만들어 똑같이 좌표 없이 `event_generate('<Button-1>')`를 호출해봤다 — 역시
콜백이 호출되지 않았다. `x=5, y=5`를 주니 이 최소 재현에서는 성공했다. 그런데 그 좌표를
그대로 실제 `_ask_combined_input_popup()` 테스트 헬퍼에 적용해도 여전히 실패했다 — 위젯
경로(`.!frame.!frame.!label2`, 여러 겹 중첩된 Frame 안)가 최소 재현보다 훨씬 깊었다.
다시 최소 재현 스크립트로 돌아가 이번엔 `target.update_idletasks()`를 이벤트 발생 직전에
추가로 호출해봤더니 성공했고, 이 한 줄을 실제 테스트 헬퍼(`_j10_run_click_probe`)에도
추가하자 즉시 통과했다.

결론: 이 환경(Windows Tk)에서 합성 마우스 클릭 이벤트가 바인딩을 실제로 트리거하려면
(1) 위젯 내부 좌표(`x=`, `y=`)가 필요하고, (2) 그 위젯이 geometry를 이미 확정한
상태여야 한다(`update_idletasks()`로 강제). 둘 중 하나만 있어도 안 될 수 있다 — 좌표
없이는 최소 재현조차 실패했고, 좌표만으로는 깊이 중첩된 실제 위젯에서 실패했다. 두 조건이
모두 충족돼야 성공했다. 이 함정은 예외를 던지지 않고 그냥 아무 일도 안 일어나므로, "위젯이
존재하고 cursor가 hand2인지"만 확인하는 테스트(`test_j10c`)는 클릭 배선 자체가 빠진
회귀를 잡지 못한다 — 실제 이벤트를 발생시켜 콜백이 불렸는지까지 검증하는 별도 테스트
(`test_j10e`)가 필요했던 이유다.

## PowerPoint `Application.Visible=True`는 프레임 창을 실제로 보이게 하지만, 포그라운드(포커스)를 가져가지는 않는다(실측 확인)

**발견 경위 (2026-09-26, §J그룹 배치4/J7):** 코디네이터 요구사항은 "PowerPoint 백그라운드
실행 안내를 추가하되, `Application.Visible=True`(변경 금지 제약)가 실제로 사용자 화면의
포커스를 훔치는지 실측하고, 훔친다면 `app.HWND` + `win32gui.ShowWindow(hwnd,
SW_SHOWMINNOACTIVE)`류로 고칠 수 있는지 검토하라"는 것이었다.

첫 시도로 `win32com.client.Dispatch("PowerPoint.Application")` 직후 `app.HWND`에 접근했더니
`com_error: Member not found`가 났다 — PowerPoint의 late-bound `Application` 객체에는애초에
`HWND`라는 멤버 자체가 없다(Word/Excel의 `Application.Hwnd`와 다르다). 이 사실만으로도
`ShowWindow()` 경로 자체가 COM 인터페이스 레벨에서 막혀 있음을 확인했다.

실제 프레임 창을 찾기 위해 `win32gui.EnumWindows()`로 전체 창을 순회해 클래스명이
`PP12FrameClass`인 창을 찾았다. 이 창은 `IsWindowVisible()=1`, `IsIconic()=0`이었다 —
즉 `Application.Visible=True`가 실제로 창을 화면에 노출시킨다(작업표시줄에 나타남,
최소화되지 않음)는 것을 확인했다. 기존 안내 문구 "화면에 창이 뜨지 않습니다"는 이 실측과
정면으로 어긋난다.

그다음 `win32gui.GetForegroundWindow()`를 (1) Dispatch 직후, (2) 실제 `count_slide_lines()`
가 쓰는 `Presentations.Open(WithWindow=False)` 측정 도중 각각 확인했다 — **두 시점 모두
포그라운드 창이 원래 작업 중이던 터미널 창 그대로였다**(PowerPoint 프레임으로 바뀌지
않음). 클린 상태에서 1회, 이전 크래시로 남은 좀비 인스턴스에 재접속한 상태에서 1회, 총
2회 반복해도 결과가 같았다. `shutdown()` 호출 후에는 `PP12FrameClass` 창이 확실히
사라지는 것까지 매번 확인해(좀비 프로세스 방지) 실측 스크립트 자체가 새 좀비를 남기지
않도록 했다.

결론: 포커스 탈취는 실제로 일어나지 않는다(그리고 애초에 `app.HWND`가 없어서
`ShowWindow`류 수정 자체가 불가능하기도 하다). 코드 수정 범위를 "안내 팝업 추가 +
문구 정정"으로 한정했다 — `ppt_com_verify.py`의 `_ensure_app()` print와 새 GUI 안내
(`_show_powerpoint_background_notice()`) 둘 다 "화면에 창이 뜨지 않습니다" 대신
"작업표시줄에 잠깐 나타날 수 있지만, 지금 쓰고 있는 창의 포커스를 가져가지는 않습니다"로
정정했다. 이 사례는 "실측 없이 요구사항의 전제(포커스를 훔칠 것이다)를 그대로 받아들이지
않고, 코드 수정 전에 먼저 실제로 측정해 전제 자체가 틀렸을 가능성을 확인한다"는 원칙의
실제 적용 사례이기도 하다.

## 서로 다른 목적의 캐시 계층이 겹칠 때, 한 계층의 스냅샷을 다른 계층의 최종 판단에 재사용하지 않는다

**발견 경위 (2026-09-27, K그룹 — K1 OneDrive 브라우저 재귀 프리페치 + K2 로컬 캐시
재사용, 리뷰 라운드17):** 코디네이터가 명시한 K1/K2 두 요구사항 사이에 "시너지"를 만들
기회가 있었다 — K1이 3개 허용 루트 폴더 아래 모든 하위 폴더/파일을 재귀적으로
`cache[parent_path]`(Graph API의 children 목록, 각 항목에 `lastModifiedDateTime`/`eTag`
포함)에 미리 채워두므로, K2가 "이 파일을 재다운로드해야 하는지" 판단할 때 이미 K1이

구현 당시(`_lookup_remote_item_metadata()`)에는 이걸 "K1/K2 시너지"로 긍정적으로 서술하고,
`test_k2f`로 "K1 캐시가 있으면 `get_item_metadata`를 호출하면 안 된다"는 걸 명시적으로
고정했다.

독립 코드 리뷰(`ooxml-code-reviewer`)가 이 시너지 자체를 의심했다 — K1의 캐시는 "그
폴더를 프리페치(또는 사용자가 한 번 펼침)한 시점"에 고정된 스냅샷이고, 팝업이 열려 있는
동안 전혀 갱신되지 않는다(`_cached_onedrive_children()`의 "이미 있으면 재사용" 계약
때문에, 사용자가 같은 폴더를 다시 봐도 새로고침되지 않는다). 반면 K2가 실제로 필요한 건

를 직접 호출해 재현했다:

- 로컬 매니페스트 기록: `lastModifiedDateTime = 2026-08-01`(지난주)
- K1 프리페치 캐시(`cache[parent_path]`)의 같은 파일 항목: 그것도 `2026-08-01`(프리페치
  시점의 스냅샷 — 매니페스트를 기록한 그 다운로드 때 함께 캐시된 값이라 둘이 일치하는
  게 당연하다)
- `get_item_metadata()`를 스텁으로 실제 실행하면(만약 호출됐다면) `2026-09-27`(오늘) 반환
  — 즉 OneDrive 쪽은 실제로 바뀐 상태

결과: `_lookup_remote_item_metadata()`가 K1 캐시에서 매칭되는 항목을 찾자마자 그걸
반환하고 `get_item_metadata()`를 아예 호출하지 않았다. `_resolve_onedrive_download()`는
"매니페스트 기록(`2026-08-01`) == 반환된 메타데이터(`2026-08-01`)"로 판정해 재사용을
결정했고, `download_calls == []`(재다운로드 없음), 반환된 파일은
`STALE-CACHED-CONTENT-FROM-LAST-WEEK`였다. 사용자가 명시적으로 강조한 핵심 불변조건
("OneDrive 쪽이 캐시 기록 시점보다 최신이면 이름이 같아도 반드시 재다운로드")이 정확히
이 경로에서 깨졌다.

**왜 기존 테스트가 못 잡았는지:** `test_k2b`(불변조건 전용 테스트)는 항상 `cache={}`로
호출해 `get_item_metadata`가 매번 실제로 불리는 경로만 검증했다 — K1 캐시가 존재하는
경우를 아예 다루지 않았다. `test_k2f`(K1/K2 시너지 전용 테스트)는 K1 캐시 값과 매니페스트
값이 둘 다 "아직 안 바뀐" 일치 케이스만 검증했다 — 즉 "K1 캐시가 프리페치 이후 실제로
stale해진" 교집합 케이스는 두 테스트 어디에도 없었다. 각 최적화를 독립적으로 검증하는
테스트만 있었고, 두 최적화가 실제로 겹쳐 상호작용하는 지점을 직접 재현하는 테스트가
없었다는 것이 사각지대의 정확한 원인이다.

**수정:** `_lookup_remote_item_metadata()`를 완전히 삭제했다. `_resolve_onedrive_
download()`는 이제 `cache` 인자와 무관하게 항상 `missa_onedrive.get_item_metadata(
remote_path)`를 직접·실시간으로 호출해 신선도를 판단한다. K1의 `cache`는 이제
`_resolve_onedrive_download()`의 최종 판단에 전혀 관여하지 않고, 트리 UI 표시(폴더
확장 시 `_cached_onedrive_children()`을 통한 네트워크 스킵)라는 원래 목적으로만
쓰인다 — 리뷰어 표현대로 "K1 캐시는 트리 표시용으로만, K2 최종 판단과 분리"가 가장
단순하고 안전한 경계였다. 다운로드 대상 파일 1개당 `get_item_metadata()` 정확히 1회만
추가로 호출되므로 API 비용 증가는 무시할 수준이고, 애초에 K1이 아꼈던 API 호출 수(트리
전체를 미리 훑는 프리페치 자체)에 비하면 미미하다.

**재현 테스트 고정:** 리뷰어의 재현 시나리오를 그대로 `test_k2i_redownloads_when_k1_
cache_and_manifest_agree_but_are_both_stale`(매니페스트=K1캐시=`2026-08-01`로 "서로는"
일치, 실시간 응답만 `2026-09-27`로 다름)로 작성해 수정 전 코드로 RED를 재확인한 뒤 수정,
GREEN 전환했다. 버그였던 동작을 정확히 요구하던 기존 `test_k2f`는 삭제하지 않고 반대
방향(K1 캐시가 있어도 실시간 조회가 실제로 호출됨, 콜 카운트로 확인)으로 뒤집어
`test_k2f_final_decision_always_calls_live_metadata_ignoring_k1_cache`로 대체했다.

**일반화:** 이 사례는 위 "post-write 재조정 이후 값을 참조할 때는 최신 상태를 다시
측정" 항목(OOXML 슬라이드 파이프라인의 "계획값 vs 실제 물리 상태")과 정확히 같은 계열의
함정이 완전히 다른 도메인(로컬 프로세스 캐시 vs 원격 API 상태)에서 재현된 것이다 — "이
값을 이미 어딘가에서 조회해서 갖고 있다"는 사실이 "이 값이 지금도 유효하다"를 보장하지
않는다. 최적화(API 호출 절약, 재계산 회피)를 위해 캐시를 재사용하기 전에는, 그 캐시가
"언제 갱신되는지"와 "지금 필요한 질문이 그 갱신 주기 안에서 답할 수 있는 질문인지"를
먼저 확인해야 한다.
