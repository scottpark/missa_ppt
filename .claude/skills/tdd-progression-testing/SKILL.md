# TDD Progression Testing

프로그레션 테스트(progression test)는 **아직 존재하지 않는 새 동작**을 구현 전에 명세하는
테스트다. `test_missa_regression.py`의 회귀 테스트(**이미 검증된 기존 동작**이 안 깨지는지
지키는 것)와 목적이 다르므로 별도 파일 `test_missa_progression.py`에 작성한다. 이 둘을 같은
파일에 섞으면 "이 테스트가 지금 뭘 지키는 건지"가 흐려진다.

## 왜 별도 파일인가

- `test_missa_regression.py`의 `MASS_CASES`는 이미 검증된 미사 유형(주일/평일)의 안정된
  픽스처에 대해 돈다. 여기에 아직 안정화되지 않은 신규 기능의 테스트를 섞으면, 신규 기능이
  불안정한 동안 회귀 스위트 전체가 자주 빨갛게 되어 "회귀 테스트는 원래 자주 깨진다"는 잘못된
  습관이 생긴다
- 프로그레션 테스트는 **일시적**이다. 기능이 안정되면 `regression-qa`가 이 중 대표 케이스를
  골라 `test_missa_regression.py`의 `MASS_CASES`/테스트 클래스로 "승격"시키고,
  `test_missa_progression.py`에서는 제거한다(아래 "승격 이후" 참고). 즉 이 파일은 항상
  "현재 진행 중인 작업"만 담아야 정상이다

## 절차 (설계서 항목 하나당 반복)

`_workspace/01_architect_design.md`의 "완전 신규"/"파라미터 분기 필요" 표 각 행이 하나의
TDD 사이클 단위다.

### 1. Red — 실패하는 테스트를 먼저 쓴다

- 설계서의 한 항목을 골라, 그 항목이 요구하는 동작을 pytest 테스트로 옮긴다
- **아직 구현이 없으므로 반드시 실패해야 한다.** `pytest tests/test_missa_progression.py::<테스트명> -v`로
  실행해 실패를 직접 확인한다(임포트 에러로 인한 "실패"가 아니라, 의도한 지점에서 assertion이
  틀려서 실패하는지 확인 — 임포트 에러면 함수 스텁이라도 먼저 만들어 실패 지점을 assertion까지
  끌고 온다)
- **약한 단언을 쓰지 않는다.** 이 프로젝트에서 "텍스트가 존재한다"만 확인하는 검증이 "텍스트는
  남고 색상만 사라지는" 버그를 통과시킨 전례가 있다(`CLAUDE.md` "검증: 텍스트 존재가 아니라
  절 번호별 오렌지색 렌더링을 확인" 참고). 아래 강한 단언 패턴을 우선한다:

  | 약한 단언 (지양) | 강한 단언 (지향) |
  |---|---|
  | 슬라이드에 특정 텍스트가 존재하는가 | 그 텍스트가 특정 run에서 특정 서식(색상/폰트)으로 렌더링됐는가 |
  | 함수가 예외 없이 끝났는가 | 저장된 파일을 `validate_pptx_structure()`로 열어 구조 손상이 없는가 |
  | 슬라이드 개수가 늘었는가 | 늘어난 슬라이드의 특정 위치에 특정 내용이 정확히 들어갔는가(순서 포함) |
  | `find_sections()`가 키를 반환하는가 | 그 키가 가리키는 슬라이드 인덱스의 실제 텍스트가 기대한 내용과 일치하는가 |

- 새 참조 PPT 템플릿을 다루는 테스트라면, `mass-template-analysis`/`boundary-verification`
  스킬의 덤프 스크립트로 실제 슬라이드 인덱스·텍스트를 먼저 확인한 뒤 그 실측값을 테스트에
  하드코딩한다(추측 금지 — 이 프로젝트 전체의 원칙과 동일)

### 2. Green — 최소 구현으로 테스트를 통과시킨다

- `ooxml-pitfalls` 스킬 체크리스트를 지키며 최소한의 코드로 테스트를 통과시킨다
- 이 단계에서 다른 기존 회귀 테스트를 깨뜨리지 않는지도 확인한다(전체 구현이 끝난 뒤가 아니라
  사이클마다 — 문제를 조기에 잡기 위함). 단, `test_missa_regression.py -v` 전체를 매번 돌리지
  않는다 — 지금 건드린 코드와 직접·간접 관련된 클래스/파일만 `-k`나 `::클래스명`으로 좁혀
  돌린다(2026-09-24 정책, ppt-ooxml-specialist 에이전트 정의 "테스트 실행 범위" 참고). 전체
  스위트는 모든 항목이 green이 되어 리뷰를 요청하기 직전 한 번만 돌린다

### 3. Refactor — 통과 상태를 유지하며 정리

- 테스트가 green인 상태를 유지하며 중복 제거, 기존 유틸 재사용으로 정리
- 리팩터 후 다시 두 테스트 파일 모두 통과하는지 확인

## 승격 이후 (regression-qa 담당, specialist는 알아만 둘 것)

기능이 안정되고 리뷰·QA를 통과하면, `regression-qa`가 `test_missa_progression.py`의 테스트를
`test_missa_regression.py`의 구조(단위 테스트 클래스 또는 `MASS_CASES` 신규 항목)로 옮기고
원본은 파일에서 제거한다. `test_missa_progression.py`가 계속 늘어나기만 한다면 승격이 밀리고
있다는 신호다.
